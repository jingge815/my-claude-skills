# 通用模式：通用技术文档

进入本模式前已按 SKILL.md 完成模式判定。本文件给出通用模式的专属流程、骨架与自检；写作语言、段落衔接、图表、缩进等通用规范以 SKILL.md 为准。

## 定位

就一个主题、模块、技术方案或代码库撰写技术说明文档，不依赖 request/design/implement 过程文档链。读者可能是接手的开发者、协作方、技术负责人或评审者；写法上比交付模式更偏连贯叙述，标题仅在必要处使用。

## 专属原则

- **不编造。** 没有材料或代码支撑的过程、数据、结论一律不写。材料之间冲突时列出分歧并请用户裁决，不自行取舍。
- **核心目标先确认。** 从用户材料提炼一句话核心目标后，向用户确认再动笔。
- **范围由用户定。** 文档目的、读者、覆盖范围、深度在阶段零与用户对齐；用户未说的按"接手工程师能独立读懂"为默认。

## 工作流程

### 阶段零：对齐目标与范围

- 与用户确认四件事：文档目的（说明、交接、评审、教学）、读者、覆盖范围、篇幅与深度。
- 从材料提炼一句话核心目标，列内部表（核心目标、现有基础、关键缺口、目标产物、边界），向用户确认。

### 阶段一：资料收集

- 清点用户材料：口述、文档、代码仓库、链接、图。
- 阅读相关代码：入口、主调用链、核心函数、数据结构、对外接口、配置项，记下准确行号。
- 材料或代码不足以支撑某章时，先向用户提问补齐，不在证据缺失处硬写。

### 阶段二：组织内容

- 把材料映射到通用骨架，确定裁剪：哪些章节保留、合并、删除。
- 对每个关键机制回答四问：现状是什么、为什么重要或不足、如何实现、如何服务核心目标。
- 区分"既有背景"和"本文重点"：背景进概述，重点进流程与机制章节；不把背景写成本文成果。

### 阶段三：核对证据（有验证或实验章节时）

- 可运行的验证照实执行并记录；复用已有结果标注来源与环境。
- 无法验证的内容如实写"未验证"及原因，不推断通过。

### 阶段四：按骨架撰写

- 见下方"通用骨架"；图表规范、章节导语、段落衔接按 SKILL.md 执行。
- 用户指定大纲时按其组织，必要信息映射到对应章节并同步更新引用。

### 阶段五：自检

- 执行 SKILL.md 共享清单与下方"专属自检清单"。

## 通用骨架（可裁剪）

默认骨架如下；章节按题材增删合并，但**概述、总体方案与流程（含总体图）、关键技术点三章必须有**，每个保留章节都必须有导语段。裁剪后在概述里说明本文覆盖了什么、没覆盖什么。图表编号按实际出现顺序连续编排。

### 一、概述

- 1 段：背景与核心目标，按"现有基础 → 关键缺口 → 本文要讲清什么"组织（80–180 字）。
- 1 段：内容组织说明，各章讲什么、如何衔接，一句带过（60–120 字）。

```markdown
## 一、概述
　　【现有基础】已经能够【…】，但【关键缺口】，因此【核心目标一句话】。本文围绕该目标，讲清【输入 → 核心处理 → 产物 → 验证】的完整链路。

　　为此，本文首先在第二章给出总体方案与流程，然后在第三章展开【N】个关键技术点，接着在第四章说明【实现/使用细节】，最后给出验证结果与总结。
```

### 二、总体方案与流程（必须）

- 先 1～2 段文字概述技术路线：各阶段职责、输入输出、衔接方式，用"首先、然后、其次、最后"串联；再以"如图 1 所示"引出总体图。
- 总体图用 Mermaid `flowchart LR`，主路径 5–9 个节点，突出核心环节；去掉核心环节图仍成立则重画。
- 涉及 3 个及以上组件时可加模块关系表。

### 三、关键技术点（必须）

- 先 1 段总述：为目标需要什么条件、现有做法的不足、总体方法。
- 再 1–3 个关键机制，每个 1 段（100–300 字）：先用"旨在"说明目的，再讲技术路线与步骤、为什么能从原理上解决、代码或材料位置。
- 不服务核心目标的机制不写；机制多且相互独立时才分小节标题，否则连贯段落表达。

```markdown
## 三、关键技术点
　　为了达成【核心目标】，需要同时保证【必要条件】。现有做法【不足】，因此本文采用【总体方法】，通过【机制 A】与【机制 B】实现。

　　**【机制名称】**旨在【机制目的】。采用【技术路线】，首先【步骤一】，然后【步骤二】。这样通过【解决原理】避免【原有问题】，实现位于 `path/file.py:函数名`。
```

### 四、实现说明（可选，涉及代码时）

- 关键文件与函数、数据结构与接口，动机先行：为什么需要、记录什么、如何使用。
- 清单类信息用表格（带表题），叙述部分保持段落。

### 五、验证或实验（可选）

- 先 1 段说明验证方法与分层思路，再以表格列出命令、结果与证据状态；证据三态标注见 SKILL.md 原则 6。
- 无可验证内容时不设本章，并在概述中说明。

### 六、总结与展望

- 1 段总结：回扣核心目标，说清读者现在知道了什么。
- 遗留问题或后续方向逐条列出，每条须有材料或代码依据；没有则写明已核对的范围。

## 篇幅参考

未另行指定时，正文 3000–12000 字，按题材密度取舍，不凑字数：

| 部分 | 参考篇幅 |
|------|----------|
| 概述 | 250–400 字 |
| 总体方案与流程 | 150–600 字 + 1 图 |
| 每个关键技术点 | 100–300 字 |
| 实现说明、验证 | 按内容密度 |
| 总结与展望 | 100–300 字 |

## 专属自检清单

与 SKILL.md 共享清单配合使用：

- 核心目标是否已向用户确认；全文是否围绕它展开。
- 是否存在无材料或代码依据的内容；材料冲突是否已请用户裁决，未自行取舍。
- 骨架裁剪是否合理：概述、总体图、关键技术点三章是否都在；被裁掉的章节是否在概述中说明。
- 有验证章节时是否标注证据状态；无验证章节时是否说明原因。
- 标题是否从简：仅在大逻辑分块或分步骤处设标题，叙述内容是否段落化。
- 用户指定的读者、范围、深度是否满足。
- 文档标识是否已与用户确认；同标识旧文档是否在原文件上更新。
