# 技术文档生成工具

把一项工作的技术内容重新组织成一份面向读者的文档。支持两种模式：

- **通用模式**：就一个主题、模块、技术方案或代码库写技术说明文档，不依赖开发过程文档。
- **交付模式**：一项需求走完需求、设计、实施、评审修复全流程后，以最终代码为事实依据，把散落在四类过程文档里的信息重组成交付文档。

判断标准（两模式通用）：把它交给一个没参与过这项工作、也不打算翻其他文档的工程师，他读完能说清楚核心目标、为什么需要它、原理和主流程，能根据文中的文件和函数直接找到实现，能照着文中的命令复现验证结果（有验证章节时），并知道还有哪些问题没解决。

两模式共用本文件的写作规范与自检清单；确定模式后，先读对应的 `references/mode-general.md` 或 `references/mode-delivery.md`，按其中的流程与模板执行。

## 何时使用本技能

- **通用技术文档**：用户要就某个主题、模块、技术方案或代码库写一份技术说明文档，没有对应的开发过程文档链。典型输入是"给这个模块写份技术文档""总结一下这个方案""写一篇技术说明"。
- **交付总结文档**：需求的实施与评审修复已经结束，代码基本定稿，用户要一份最终可看、可交付的技术文档。

交付模式在整条链路的最后一环：`requirement-doc` → `tech-design-doc` → `tdd-implement` → `code-review-doc` →（`tdd-implement` 修复）→ 本技能。链路位置、就绪检查等细节见 `references/mode-delivery.md`。

## 模式判定

动笔前先确定模式；判定不准时向用户确认，不猜。

进入**通用模式**的条件（满足任一）：
- 用户给的是主题、模块、方案或代码库，`docs/` 下没有同标识的 request/design/implement 文档链；
- 用户要的是"普通技术文档""技术说明""方案总结"，不是某次需求的交付总结。

进入**交付模式**的条件（满足任一）：
- `docs/` 下存在同标识的 request/design/implement 文档链，且用户要这次改动的最终交付文档；
- 用户明确说"生成 techdoc""出个交付文档""把这次改动整理成技术说明"。

"写技术文档"这类模糊表述两模式都可能命中：先查 `docs/` 下的过程文档链与用户意图，再定模式。

## 不可违背的原则

1. **事实是唯一依据。** 交付模式以最终代码为事实依据：文档描述当前代码的真实行为，不是设计文档里的计划；过程文档与代码不一致时以代码为准，并记录到"与设计的差异"。通用模式以用户提供的材料与实际代码为依据；没有依据的内容不写，材料之间冲突时列出分歧并请用户裁决。
2. **全文围绕一个核心目标展开。** 动笔前先提炼一句话的核心目标，写成内部目标卡。流程图、机制、问题章节都必须回答"这一步如何服务核心目标"。与目标无关的通用流程、泛化机制和局部修复不进入这些章节。流程图中必须出现关键环节；去掉它图仍成立，说明图没有围绕目标。
3. **遵循本文件的写作规范。** "写作语言规范""图表规范""文档表达规范"对两模式同等生效。
4. **每条技术结论都必须可追溯。** 涉及实现的描述附 `文件:行号` 或 `文件:函数名`，且必须是本次实际打开过的位置；涉及需求覆盖的描述对应到需求编号（交付模式）。不写"看起来合理"但没核实过的路径或机制。
5. **必须有总体图。** 流程或架构章节先用 1～2 段文字概述技术路线，再用紧凑图覆盖输入、核心处理、交付产物、结果验证和目标环境（按题材裁剪）。
6. **验证结论必须对应可追溯的证据**（有验证章节时）。区分"本次实际验证""复用已有验证""仅核对实现但未执行"。不得将操作示例或未执行命令写成实测成功。
7. **关键问题必须有出处，不能编造。** 问题章节每条必须来自过程文档、用户提供的材料或代码与测试能直接确认的事实，并标注来源。不能为了显得有深度而虚构难点。
8. **只陈述，不新增决策和建议。** 不改代码、不提新功能或新优化。遗留问题章节只汇总已有记录或代码与测试能直接确认的问题。
9. **文件命名固定为：** `docs/techdoc-<标识>-<YYYYMMDD>.md`。交付模式沿用前序文档已使用的标识；通用模式从主题提炼简短标识，与用户确认。同一标识已存在技术文档时，在原文件上更新，不另建新文件。
10. **默认采用对应模式的模板和篇幅预算。** 用户指定大纲、篇幅或完整覆盖要求时优先遵从，不为满足预算删除必要内容；调整章节后同步更新交叉引用与自检项。

## 通用表达模型

技术文档按以下抽象层次组织：

1. **目标主线**：核心目标是一句话。先写"现有基础 → 关键缺口 → 本次内容 → 目标产物"，再展开各章。每一节的导语都要回到这句话，不能从通用流水线或文件清单开始。
2. **流程表达**：以核心目标为主线，按"现状与输入 → 关键环节 → 交付产物 → 结果验证 → 目标环境"组织。图必须突出关键节点，而不是一条去掉本次内容仍然成立的通用流水线。
3. **机制展开**：每项机制按"目的 → 技术路线 → 实施步骤 → 解决原理 → 代码位置"展开。
4. **变更说明**（涉及代码改动时）：每项结构或接口按"功能需求 → 所需信息 → 已有不足 → 新增或修改 → 兼容影响"展开。
5. **验证组织**（有验证章节时）：组合既有回归、新特性测试、产物检查和端到端验证，并说明各层分别排除什么风险。

交付模式补充的"需求对齐"与"评审闭环"见 `references/mode-delivery.md`。

模板与骨架只使用中性占位符，不写死某个项目的业务链路、产品名称或领域术语；实际文档必须把【核心目标】等占位替换为本项目的真实内容，并在概述、流程、机制章节反复回扣，不能只出现一次。

## 写作语言规范

文档的首要目标是可读。读者可能是接手的开发者、测试人员或技术负责人。

**允许使用英文的只有两类：**
- 代码标识符：文件路径、函数名、类名、字段名、配置项、命令、错误信息原文。一律用反引号包裹，如 `build_filename()`、`pytest -q`。
- 通用技术专有名词：HTTP、JSON、SQL、Git、Mermaid、LRU、API、CPU 等。首次出现且读者可能不熟悉时，后面用括号给一句中文解释。

**除非英文专有名词，其他都用中文。** 禁止在中文句子里夹英文普通词汇。常见改写对照：

| 禁止写法 | 改为 |
|----------|------|
| 做了 refactor / fix 掉了 | 做了重构 / 修复了 |
| 这个 case / corner case | 这个场景 / 边界场景 |
| 走 fallback 逻辑 | 走兜底逻辑 |
| support 一下 / handle 不了 | 支持 / 无法处理 |
| 性能 OK / 结果 match | 性能达标 / 结果一致 |
| 加了个 cache 层 | 增加了缓存层 |
| PR / commit 里改了 | 在合并请求 / 提交中修改了（Git 术语可保留 `commit` 作为命令参数） |

**句子：**
- 一句话只说一件事，单句不超过 40 字。
- 不用"非常""极大地""显著"等修饰词，用数字或事实代替。
- 同一概念全文用同一个词，不要"缓存""缓冲""暂存"混用。

**段落与衔接：**
- 段落不超过 5 句，先说结论再说原因。
- 一段只推进一个论点；句间关系显性选词，按真实逻辑选用：因果（由于、因此）、递进（进一步）、转折（然而）、并列（同时），不堆砌连接词。
- 段内句子按"论点 → 依据 → 推论"或"现状 → 不足 → 对策"组织，句句围绕本段论点。
- 段落之间承上启下：后一段首句承接前一段的关键结论或引出其局限，凭空另起话题不合格。承接靠实质内容——复指前段结论的关键词、指出前段方案引出的新问题、在前段基础上继续推进。
- 承上启下不等于加过渡句：禁止"下面我们来看""值得一提的是""不难发现"这类空转铺垫；衔接写在句子的内容里，不写成独立套话。
- 章节之间同样衔接：每章导语段的第一句承接上一章的结论，再总述本章。

## 图表规范

图、表分别全文连续编号：图 1、图 2…，表 1、表 2…；不按章节重新编号，删除图表后其余编号顺延重排。

**文字先行：**任何图表之前必须有正文说明其目的与阅读重点，并用"如图 1 所示""见表 1"引出；读者先读到文字，再看到图表。每个图、表在正文中至少被引用一次，没有引用的孤儿图表删除或补引用。图后仅补充关键机制或结论，不逐项复述图中内容。

**题目：**图题在图下方，表题在表上方，均居中，格式为"图 N　题目""表 N　题目"（编号与题目之间空一格）。Markdown 中居中统一用 `<p align="center">图 1 总体处理流程</p>`；该标签与其前后的表格、代码块之间各留一个空行，否则部分渲染器不渲染相邻元素。

**位置：**章节标题后的第一块内容必须是导语段，图、表、代码块、列表不得紧跟标题出现；图表置于所属段落之后，不插在自然段中间打断句子。

**尺寸与可读性：**
- Mermaid 流程图默认 `flowchart LR` 横向布局；主路径 5–9 个节点，按技术阶段抽象；节点文字最多两行；避免竖向长链，需要细节时在机制章节用文字展开，不拉长图。
- 图中文字颜色与阅读背景匹配：深色背景用白色文字、边框和连线，浅色背景用黑色；不确定阅读环境时询问用户。
- 表格不超过 6 列，单元格文字不超过 30 字；行数过多时拆成多表。
- 插入位图（截图、导出图）时，显示宽度不超过正文宽度、高度不超过一屏，保证缩放后文字可读。

## 文档表达规范

正文以连贯段落解释原因与机制，全文围绕核心目标组织；章节先总述再展开。

**章节导语：**每个章节标题后的第一块内容必须是 1 段总结性文字（2–5 句），概括本章讲什么、与前后章的衔接；然后才允许出现小节、图、表、列表或代码块。

**段落为主：**背景、原理、机制、问题等叙述性内容一律写成连贯段落，不拆成标题加短语。仅以下三类内容允许非段落形式：具体执行步骤用编号列表，对照类信息（参数、字段、清单、结果）用表格，命令用代码块。不为"段落为主"把对照信息强行写成长段落。

**标题从简：**默认不新增标题层级；仅当内容存在大的逻辑分块（如多个独立机制、多个阶段）或需要分步骤执行时才设小节标题。交付模式沿用其模板的既有章节结构，不额外加层。

正文自然段以两个全角空格（两个 U+3000）开头；标题、图表题目、表格、代码块和列表标记行不缩进。使用准确、连贯的中文，代码标识符与技术专有名词保留原文；实现结论以实际阅读过的代码为依据，验证结论按证据状态表述。

## 标准工作流程

两模式共用以下骨架；各阶段在对应 reference 文件中有模式专属的展开：

- **阶段零：提炼核心目标与差距。** 交付模式从 `request` 摘一句话核心目标；通用模式从用户材料提炼，并向用户确认。用一张内部表记录：核心目标、现有基础、关键缺口、目标产物、边界。后续每节写作都对照这张表；无法回答"服务哪个目标"的内容不进叙述章节。
- **阶段一：资料收集与就绪检查。** 按 `references/mode-delivery.md` 或 `references/mode-general.md` 的流程执行。
- **阶段二：基于代码重建事实。** 确定讲述范围；阅读入口、主调用链、核心函数、关键数据结构、对外接口、配置项，记下准确行号；对每个关键点回答四问：现状是什么、为什么不足或重要、做了什么或如何实现、如何服务核心目标。涉及文件较多或代码不熟悉时，通过 Agent 工具委托子代理阅读，要求其汇报文件路径、函数职责、调用关系和行号；支撑关键结论的部分自己再核实。
- **阶段三：核对证据与必要验证。** 有验证章节时执行；区分"本次实际验证""复用已有验证""仅核对实现但未执行"，复用证据核对来源、代码基线与环境；不为写文档默认跑全量回归、新增测试代码。
- **阶段四：内容提炼与撰写。** 按对应模式的模板逐节撰写；用户指定大纲时按其组织，同步更新引用。图表统一使用 Mermaid（插入位图除外），遵守图表规范。
- **阶段五：自检。** 逐项执行下方清单与模式 reference 中的专属清单，任一项不满足就修改。

## 自检清单

- 模式判定是否正确；进入撰写前是否读了对应的 reference 文件。
- 是否有一句话的核心目标，概述、总体方案、关键机制各章是否围绕它展开；是否存在去掉核心内容仍成立的通用段落。
- 每个章节标题后的第一块内容是否为导语段；有无标题后直接跟图、表、代码块或列表。
- 图表是否全文连续编号；图题是否在图下、表题是否在表上且居中；是否每个图表都先有文字说明并被"如图/如表 N 所示"引用；有无孤儿图表。
- 图表尺寸是否越界：流程图节点数与方向、表格列数与单元格字数、位图宽高。
- 段落衔接抽查：每章抽 2 处相邻段，后段首句是否承接前段结论；全文搜索"下面我们""值得一提"等空转铺垫是否为空。
- 叙述内容是否段落化；列表、表格、代码块是否只用于步骤、对照、命令。
- 全文是否有中英文混杂（按语言规范对照表逐类搜一遍）。
- 每个正文自然段是否以两个全角空格开头；标题、图表题目、表格、代码块、列表是否未误缩进。
- 每条技术结论是否可追溯（`文件:行号`、`文件:函数名` 或材料出处），且为本次实际打开或核对过的位置。

## 实操要点

- **先读代码，再写原理。** 原理一节最容易写成教科书式的通用介绍。每一句都要落到具体实现：说"使用了缓存"不够，要说明缓存放在哪、键是什么、何时失效。
- **流程图只保留技术主路径。** 先用文字说明各阶段职责，再用少量节点表达输入、产物与执行环境。不要展开函数调用链，不要在图后重复步骤，不要用颜色代替职责说明。
- **验证命令照原样写。**（有验证章节时）包括参数和路径，读者复制即可运行；依赖环境变量或测试数据的，在验证环境中说明。
- **先立目标，再搭骨架。** 动笔前写一句话核心目标和一张"基础—缺口—内容"表；图先画关键节点，再补上下游。
- **围绕目标做减法。** 叙述章节只保留服务核心目标的内容；清单类章节可以全，但叙述不能按文件平铺。
- **读代码四问。** 对每个关键点回答：现状是什么、为什么不足或重要、做了什么、如何服务目标。
- **重新生成时在原文件上更新。** 内容再次变化后，更新受影响的章节，核对证据适用性，并检查图、行号、清单是否同步。
