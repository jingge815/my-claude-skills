# 最终技术文档生成工具

在一项需求的全部工作（需求、设计、实施、评审修复）完成后，以最终代码为事实依据，把散落在四类过程文档里的信息重新组织成一份面向读者的技术文档：解决了什么问题、整体流程怎么走、基于什么原理、关键难点怎么解决、改了哪些文件和函数、做了哪些验证、结果如何、还剩哪些问题。

这份文档和过程文档的区别：设计文档写"计划怎么做"，实施文档写"做事的过程"，评审文档写"哪里有问题"；技术文档写"最终系统是什么样、为什么这样、怎么证明它是对的"。

判断标准：把它交给一个没参与过本需求、也不打算翻其他文档的工程师，他读完能说清楚这个功能的核心目标、为什么需要它、原理和主流程，能根据文中的文件和函数直接找到实现，能照着文中的命令复现验证结果，并知道还有哪些问题没解决。

## 何时使用本技能

需求的实施与评审修复已经结束，代码基本定稿，用户要一份最终可看、可交付的技术文档。典型位置是整条链路的最后一环：`requirement-doc` → `tech-design-doc` → `tdd-implement` → `code-review-doc` →（`tdd-implement` 修复）→ 本技能。

如果实施还在进行、或评审问题尚未修复，先提醒用户：此时生成的文档很快会过时。用户坚持生成的，照常输出，但在 1.3 和第八节如实标注当前状态（如"存在 2 条未修复的高级别评审问题"）。

过程文档不全（比如没有设计文档）时也可以使用，但要告知用户哪些章节因缺少依据只能基于代码推断或写"无"，不要编造过程信息。

## 不可违背的原则

1. **最终代码是唯一事实依据。** 文档描述的是当前代码的真实行为，不是设计文档里的计划。过程文档与代码不一致时以代码为准，并记录到第七节"与设计的差异"。
2. **全文围绕一个核心目标展开。** 动笔前先从 `request` 提炼一句话的核心目标，写成内部目标卡。第二节流程图、第三节机制、第四节问题都必须回答"这一步如何服务核心目标"。与目标无关的通用流程、泛化机制和局部修复不进入这三节。流程图中必须出现本次新增或改造的关键环节；去掉它图仍成立，说明图没有围绕目标。
3. **文档表达遵循“文档表达规范”。**
4. **每条技术结论都必须可追溯。** 涉及实现的描述附 `文件:行号` 或 `文件:函数名`，且必须是本次实际打开过的位置；涉及需求覆盖的描述对应到需求编号（R1、R2…）。不写"看起来合理"但没核实过的路径或机制。
5. **必须有总体流程图。** 第二节先用 1～2 段文字概述技术路线，再用紧凑流程图覆盖输入、核心处理、交付产物、结果验证和目标环境。背景透明，默认使用白色文字、边框和连线；明确使用浅色主题时再改为黑色。
6. **验证结论必须对应可追溯的证据。** 区分“本次实际验证”“复用已有验证”“仅核对实现但未执行”。复用结果记录来源、代码基线（含相关未提交改动）与环境，并核对适用性；相关代码变化或证据缺失时，仅补做必要验证。不得将操作示例或未执行命令写成实测成功。
7. **关键问题必须有出处，不能编造。** 第四节每条问题必须来自需求文档、设计文档、实施文档或评审文档，并标注来源章节。不能为了显得有深度而虚构难点。
8. **只陈述，不新增决策和建议。** 不改代码、不提新功能或新优化。第八节只汇总过程文档已记录、或代码与测试能直接确认的问题。
9. **遵守写作语言规范，默认采用下方模板和篇幅预算。** 用户指定大纲、篇幅或完整覆盖要求时优先遵从，不为满足预算删除必要内容；调整章节后同步更新交叉引用与自检项。
10. **文件命名固定为：** `docs/techdoc-<需求简称或唯一标识>-<YYYYMMDD>.md`，标识沿用前序文档已经使用的标识。同一标识已存在技术文档时，在原文件上更新，不另建新文件。

## 通用表达模型

技术文档按以下七个抽象层次组织。模板只能使用中性占位符，不能把某个项目的业务链路、产品名称或领域术语写成固定示例。

1. **需求对齐**：`request` 说明为什么做、目标是什么、哪些边界必须保留；最终代码说明实际做成了什么。
2. **目标主线**：核心目标是一句话。先写“现有基础 → 关键缺口 → 本次改造 → 目标产物”，再展开各章。每一节的导语都要回到这句话，不能从通用流水线或文件清单开始。
3. **流程表达**：以核心目标为主线，按“现状与输入 → 为达成目标新增或改造的环节 → 交付产物 → 结果验证 → 目标环境”组织。流程图必须突出本次新增或改造的节点，而不是一条去掉本次改动仍然成立的通用流水线。
4. **机制展开**：每项机制按“目的 → 技术路线 → 实施步骤 → 解决原理 → 代码位置”展开。
5. **变更说明**：每项结构或接口按“功能需求 → 所需信息 → 已有不足 → 新增或修改 → 兼容影响”展开。
6. **验证组织**：组合既有回归、新特性测试、产物检查和端到端验证，并说明各层分别排除什么风险。
7. **评审闭环**：按“核心问题 → 修复状态 → 最终证据”列表呈现，跨轮问题以最终状态为准。

模板保持中性占位符；实际文档必须把【核心目标】替换为本需求的一句话目标，并在 1.1、2.1、3.1 和第四节反复回扣，不能只在 1.1 出现一次。

## 写作语言规范

文档的首要目标是可读。读者可能是接手的开发者、测试人员或技术负责人。

**允许使用英文的只有两类：**
- 代码标识符：文件路径、函数名、类名、字段名、配置项、命令、错误信息原文。一律用反引号包裹，如 `build_filename()`、`pytest -q`。
- 通用技术专有名词：HTTP、JSON、SQL、Git、Mermaid、LRU、API、CPU 等。首次出现且读者可能不熟悉时，后面用括号给一句中文解释。

**除非英文专有名词，其他都用中文。** 禁止在中文句子里夹英文普通词汇。常见改写对照：

| 禁止写法 | 改为 |
|----------|------|
| 做了 refactor / fix 掉了 | 做了重构 / 修复了 |
| 这个 case / corner case | 这个场景 / 边界场景 |
| 走 fallback 逻辑 | 走兜底逻辑 |
| support 一下 / handle 不了 | 支持 / 无法处理 |
| 性能 OK / 结果 match | 性能达标 / 结果一致 |
| 加了个 cache 层 | 增加了缓存层 |
| PR / commit 里改了 | 在合并请求 / 提交中修改了（Git 术语可保留 `commit` 作为命令参数） |

**句子与段落：**
- 一句话只说一件事，单句不超过 40 字。
- 段落不超过 5 句，先说结论再说原因。
- 不用"非常""极大地""显著"等修饰词，用数字或事实代替。
- 不写铺垫和过渡句（如"下面我们来看""值得一提的是"）。
- 同一概念全文用同一个词，不要"缓存""缓冲""暂存"混用。

## 篇幅预算

未另行指定时，全文正文（不含代码块、图、表格）建议为 3000–12000 字。以下章节与篇幅均为默认参考，用户大纲和完整覆盖要求优先：

| 章节 | 作用 | 正文篇幅 | 必须包含 |
|------|------|----------|----------|
| 一、概述 | 一页看懂做了什么、做成没有 | 250–400 字 + 1 表 | 背景、方案摘要、完成情况表和总结句 |
| 二、总体流程 | 看懂系统怎么跑 | 150–600 字 + 1 图（可加 1 表） | 图前总体说明、紧凑流程图、模块关系 |
| 三、核心原理 | 看懂为什么能解决问题 | 300–600 字 | 总体方法、1–3 个关键机制 |
| 四、关键问题与解决方案 | 看懂难点怎么解决 | 每条 100–220 字，共 3–8 条 | 问题类别总述、技术方法、解决原理、位置、验证 |
| 五、改动说明 | 知道改了哪些文件和函数 | 50–500 字 + 表 | 改动统计、文件清单、核心函数清单 |
| 六、验证 | 知道怎么证明是对的 | 50–500 字 + 表 + 命令 | 命令、实际结果、验收对照 |
| 七、与设计的差异 | 知道和计划有何不同 | 表格为主 | 差异项与原因 |
| 八、当前遗留问题 | 知道还剩什么没解决 | 表格为主 | 问题、影响、来源、状态 |

## 文档表达规范

正文以连贯段落解释原因与机制，全文围绕核心目标组织；章节先总述再展开。图表前说明目的与阅读重点，图后仅补充关键机制或结论，不逐项复述。参数与日志字段对照可用表格，操作步骤可用编号列表，命令使用代码块，不为“段落为主”而将对照信息强行写成长段落。

正文自然段以两个全角空格（两个 U+3000）开头；标题、表格、代码块和列表标记行不缩进。使用准确、连贯的中文，代码标识符与技术专有名词保留原文；实现结论以实际阅读过的代码为依据，验证结论按证据状态表述。

## 标准工作流程

### 阶段零：提炼核心目标与差距

- 从 `request` 摘出一句话的核心目标，并列出交付边界。
- 用一张内部表记录：核心目标、现有基础、关键缺口、目标产物、验收边界。
- 后续每节写作都对照这张表；无法回答"服务哪个目标"的内容不进入第二、三、四节。

### 阶段一：资料收集与就绪检查

- 先读 `request` 的"目标与范围"和 `design` 的"设计结论""现状与修改依据"，再读 diff；不要先被实现细节带走。
- 在 `docs/` 下按需求标识找出 request、design、implement 以及全部 review 文档（已提交和未提交都要找），完整阅读。
- 把 `request` 的功能需求逐条抄成 R1…Rn，作为 1.3 和 6.3 的锚点。
- 检查就绪状态：实施文档的"实施结论"是否为全部完成；评审问题在实施文档"评审问题修复记录"里是否都有确认与修复结果；`git status` 是否还有与本需求相关的未提交改动。
- 记录代码基线：`git rev-parse --short HEAD` 与当前分支名。
- 就绪检查发现问题时告知用户，确认是否继续。

### 阶段二：基于最终代码重建事实

- 确定改动范围：以设计文档 5.1、实施文档 3.2 为线索，结合 `git diff --stat <需求起点>..HEAD`（或工作区 `git diff --stat`）得到真实的文件清单与增删行数。需求起点不明确时向用户确认。
- 阅读最终代码：入口、主调用链、核心函数、关键数据结构、对外接口、配置项，记下准确的行号。
- 涉及文件较多或代码不熟悉时，通过 Agent 工具委托子代理阅读，要求其汇报文件路径、函数职责、调用关系和行号；支撑关键结论的部分自己再核实一遍。
- 逐个阅读未提交代码的核心文件，不只依赖 `git diff --stat`。对每个核心改动回答四问：原实现做什么、为什么不够、本次改了什么、改后如何服务核心目标。答案直接作为第四节素材。
- 区分"基础能力"和"本次新增"：基础能力写在 1.1 和 1.2，本次新增写在第二、三、四节；不要把既有能力写成本次成果。
- 逐条核对设计文档功能点与最终代码，标记为"按设计实现""实现方式有调整""未实现或被移除"三类，作为第七节素材。

### 阶段三：核对证据与必要验证

- 找出项目的测试与检查命令（看 `package.json`、`pyproject.toml`、`Makefile`、CI 配置、实施文档里用过的命令）。
- 先核对实施、评审及已有运行记录的来源、代码基线与环境，判断各项证据是否适用于当前实现；条件未变且证据充分时直接复用，不因生成文档重复执行。
- 相关代码发生变化、证据缺失或不能支撑验收结论时，仅补做必要的测试、构建或产物检查，不默认运行全量回归，不为写文档新增测试代码。
- 每项标注“本次实际验证”“复用已有验证”或“仅核对实现但未执行”，记录命令、实际结果、证据来源、基线与环境；无法核实的信息及未执行原因如实说明，不挑选性隐去失败。
- 操作示例与实测结果分开；示例命令即使可复制运行，也不能据此标记通过。



### 阶段四：内容提炼与撰写

- 默认按下方“章节写作模板”逐节撰写；用户指定大纲时按其组织，将必要信息映射到对应章节并同步更新引用。无指定大纲时，不适用章节写“无”并说明原因。
- 图表统一使用 Mermaid。

### 阶段五：自检

逐项检查，任一项不满足就修改；采用用户大纲时，下列章节编号按实际内容映射：
- 模板与示例是否只含中性占位符，未写死具体业务链路、产品名或领域术语；实际文档是否才替换为项目事实。
- 1.1 是否贴合 `request-xxx` 的原始目标与保留边界，1.2 是否讲清总体技术路线而非局部细节。
- 第二节是否先有总体说明，再有 5–9 个主节点的紧凑流程图，默认是否使用透明白色框图，且图后没有重复步骤。
- 3.1 是否先说明目标、必要条件、现有不足和总体方法；每个机制是否先讲目的与技术路线，再讲实现。
- 每个 `文件:行号` 是否在当前代码中真实存在且指向正确内容。
- 第五节文件清单是否与 `git diff --stat` 一致，不多不少；5.4 是否先说明功能需求、已有不足和变更动机，再给定义。
- 6.2 是否先总体说明既有回归、新特性测试、产物检查和端到端验证的组合方法；每项是否注明证据状态、来源、基线与环境，复用是否仍适用，未执行项与操作示例是否未误写为实测成功。
- 需求文档中每个需求编号是否在 1.3 表中有结论。
- 第四节是否有问题类别总述，每项是否标注来源，并用连贯段落说明技术手段、解决原理、位置和验证。
- 6.4 是否列出各轮核心问题、修复状态和最终证据，而不只有数量统计。
- 各章节是否遵从用户大纲并完整覆盖要求，无另行要求时是否参考默认篇幅预算；全文是否有中英文混杂（按语言规范对照表逐类搜一遍）。
- 是否有一句话的核心目标，且 1.1、2.1、3.1、第四节都围绕它展开；第二、三、四节是否存在去掉本次核心改造仍成立的通用内容。
- 流程图是否包含本次新增或改造的关键节点，且去掉该节点后流程不再成立。
- 每个正文自然段是否以两个全角空格 `　　` 开头；标题、表格、代码块、列表符号是否未误缩进。
- 是否先读了未提交代码和 request/design，再动笔；第四节每个问题是否能对应"原有不足—本次修改—目标贡献"。
- 1.1 是否写出"现有基础—关键缺口"，而不是只写背景。

## 章节写作模板

以下为默认写作要求与模板。【】内为需要替换的内容；用户指定大纲时可重组章节，以完整覆盖必要信息为准，不受默认章节编号与篇幅约束。

### 文档头部

```markdown
# 技术文档：【需求全称】
> 文档编号：techdoc-【简称】-【YYYYMMDD】
> 创建日期：【YYYY-MM-DD】
> 关联文档：request-【…】、design-【…】、implement-【…】、review-【…】（多份逐一列出，没有的写"无"）
> 关联项目：【项目名称】
> 代码基线：【分支名】@【commit 短哈希】（有未提交改动时注明"含未提交改动"）
> 核心目标：【一句话说明本次要达成的目标】
```

### 一、概述（250–400 字 + 1 表）

**1.1 背景与问题**：1 段，80–180 字，3 句。必须以 `request-xxx` 的原始背景、核心目标和交付边界为依据，不能用实施阶段才发现的局部问题替代原始需求。

## 实操要点

- **先读代码，再写原理。** 原理一节最容易写成教科书式的通用介绍。每一句都要落到本项目的具体实现：说"使用了缓存"不够，要说明缓存放在哪、键是什么、何时失效。
- **流程图只保留技术主路径。** 先用文字说明各阶段职责，再用少量节点表达输入、产物与执行环境。不要展开函数调用链，不要在图后重复步骤，不要用颜色代替职责说明。
- **验证命令照原样写。** 包括参数和路径，读者复制即可运行。依赖环境变量或测试数据的，在 6.1 中说明。
- **差异不是缺陷。** 实施和评审中合理调整设计是正常的，如实记录原因，不要回避，也不要写成检讨。
- **过程文档也会出错。** 实施文档里的行号、测试数量，评审文档里的结论，都可能在后续修改后失效，引用前要核对当前代码、证据基线与环境是否仍然适用。
- **先立目标，再搭骨架。** 动笔前写一句话核心目标和一张“基础—缺口—改造”表；流程图先画本次改造节点，再补上下游。
- **围绕目标做减法。** 第二、三、四节只保留服务核心目标的内容；改动清单可以全，但叙述不能按文件平铺。
- **读代码四问。** 对每个核心文件回答：原来做什么、为什么不够、本次改了什么、如何服务目标。
- **重新生成时在原文件上更新。** 代码再次变化后，更新受影响的章节和"代码基线"，核对第六节证据适用性，仅补做受相关变化影响或缺失的必要验证，并检查流程图、行号、文件清单、差异表是否同步。
