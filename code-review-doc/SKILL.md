# 代码评审报告工具

以需求文档、设计文档、实施文档为唯一基准，审查 Git 工作区里未提交的变更代码，判断实现是否忠实对齐了这三份文档，并把发现的问题按严重性分级整理成一份精简、可直接拿去改代码的评审报告。

这个技能的定位是"合规校验"，不是"代码美化建议"。它不会因为看到一段代码写得不够优雅就提出改进意见——除非那段代码违反了需求、设计，或者项目已有的编码规范。个人偏好、设计外的优化想法，都不属于本技能的评审范围。

## 何时使用本技能

用户已有对应的需求文档、设计文档、实施文档，并且项目里有 Git 未提交的变更代码，想知道这些变更是否忠实执行了文档要求。典型场景是 `tdd-implement` 技能跑完之后，在提交代码前做一次独立校验，或者用户自己手写了代码想验证是否跑偏。

如果三份文档中有缺失（比如只有需求没有设计），要先向用户确认能否评审——没有设计文档就无法判断"设计符合度"这一维度，此时应明确告知这一维度无法评审，而不是跳过不说。

## 不可违背的原则

1. **评审依据唯一。** 所有问题判定必须能追溯到需求文档、设计文档，或项目现有的编码规范（如 CLAUDE.md、lint 配置、既有代码风格）。不能引入个人偏好或者"我觉得这样更好"的设计外优化建议。
2. **只评审 Git 未提交的变更。** 用 `git status`/`git diff` 确定审查范围，只针对工作区和暂存区里尚未提交的改动（新增、修改、删除的文件），不对项目里早已存在、本次未触碰的代码发表评审意见。
3. **问题描述必须三要素齐全：标准是什么、实际是什么、错在哪里。** 禁止"这段代码逻辑不太对"这种模糊定性，必须写清楚文档/规范要求的是什么，代码实际做了什么，两者之间的具体偏差点。
4. **严重性分级刚性排序。** 所有问题按"严重 > 高 > 中 > 低"从上到下排列，影响功能正确性、偏离需求或设计核心的问题必须排在前面。
5. **报告只保留问题与修改建议，不写背景介绍、不写表扬、不写通用方法论。** 如果这次评审没有发现任何问题，报告要如实说明"未发现问题"，不要为了显得有内容而堆砌无关描述。
6. **只评审不修改、不做实现决策。** 给出修改思路即可，不直接改代码；如果一个问题有多种合理的修改方式，把方向说清楚，选择权交给开发者。

## 四个评审维度

对每一处变更，都要从以下四个维度逐项校验：

1. **需求一致性**：这段改动是否在需求文档划定的范围内？是否存在需求要求但代码未实现（遗漏），或代码实现了需求之外的功能（超范围）？
2. **设计符合度**：代码的模块划分、接口定义、数据结构是否与设计文档一致？如果设计文档指定了某个函数签名、某种流程，代码是否照做？
3. **代码质量**：逻辑正确性、异常处理是否完整、边界条件是否覆盖；是否遵循最小改动原则（有没有不必要的新增类/方法/依赖、无关的重构）；注释是否符合规范（仅关键逻辑加 1-2 句中文注释，无中英文混杂的口语化表达，无冗余注释）。
4. **测试完备性**：是否遵循 TDD（有实现必须有对应测试）；测试是否真的覆盖了对应功能的正常场景和关键边界场景；是否存在测试与代码实际行为不匹配的情况（测试断言的和代码做的不是一回事）。

## 标准工作流程

### 阶段一：输入接收与基线对齐

- 接收需求文档、设计文档、实施文档的路径（或按标识在 `docs/` 目录下查找同一需求标识的三份文档）。
- 用 `git status` 和 `git diff`（包含已 staged 和未 staged 的改动）确定本次评审的代码范围，列出所有新增、修改、删除的文件。
- 从三份文档中提取评审基准：需求范围与验收标准、设计文档的模块/接口/数据结构定义、实施文档记录的任务清单与预期改动文件。
- 如果 Git 工作区没有任何未提交的变更，直接告知用户，不要凭空评审。

### 阶段二：合规性与一致性审查

- 逐个变更文件核对：这个改动对应设计文档里的哪个任务/模块？如果对应不上，判断是遗漏记录还是超范围实现。
- 检查是否有需求文档要求但本次变更中完全没有涉及的功能点（可能是漏做，也可能是分批提交中的一部分——如果实施文档显示这是有意分阶段的，就不算问题）。
- 检查是否存在设计文档之外的功能实现、无关的重构或代码优化（哪怕代码本身写得更好，只要设计没要求，就是超范围）。
- 检查最小改动原则的执行情况：有没有可以复用现有代码却重新写了一遍的地方，有没有为了这次改动引入了不必要的新依赖。

### 阶段三：代码质量与测试审查

- 对变更代码逐行/逐块审查逻辑正确性，重点看条件分支、循环边界、空值/异常处理是否完整。
- 核对注释规范：关键逻辑和复杂分支是否有恰当的中文注释（不超过两句话），是否存在解释"做了什么"而非"为什么"的冗余注释，是否有中英文混杂的表达。
- 核对是否每个新增/修改的功能点都有对应测试，测试是否真的会在功能被破坏时失败（而不是形式上存在但断言很弱）。
- 如果项目里有可运行的测试命令，实际运行一次，确认当前变更下测试的通过情况，把结果作为审查证据（而不是仅凭读代码猜测测试会不会通过）。

### 阶段四：问题整理与报告生成

- 汇总发现的所有问题，按"严重 > 高 > 中 > 低"排序：
  - **严重**：功能不正确、会导致数据错误或系统故障、完全偏离设计核心方案
  - **高**：明显超出需求/设计范围、关键测试缺失、破坏了现有功能
  - **中**：设计细节不符（如接口参数命名/顺序不一致）、边界场景遗漏、非核心逻辑的注释/规范问题
  - **低**：轻微的规范性问题（如注释风格轻微不符），不影响功能和后续维护
- 每个问题写清楚：问题说明（标准+实际+偏差点）、涉及文件（精确到路径，尽量给出函数名/行号）、修改思路（具体可执行）。
- 按下方固定模板生成报告，文件命名为 `docs/review-<需求简称或唯一标识>-<YYYYMMDD>.md`，标识沿用需求/设计/实施三份文档已经使用的标识，保持四份文档可追溯。
- 如果没有发现任何问题，评审概述里明确写"本次评审未发现需求、设计、代码质量、测试完备性方面的问题"，「二、修改建议」一节写"无"，不要编造问题凑数。

## 固定输出模板

报告要精简聚焦，严格只保留以下结构，不要额外添加背景介绍、方法论说明等无关章节。

```markdown
# 代码评审报告：【需求全称】
> 文档编号：review-【简称】-【YYYYMMDD】
> 创建日期：【YYYY-MM-DD】
> 关联需求文档：【需求文档编号】
> 关联设计文档：【设计文档编号】
> 关联实施文档：【实施文档编号】

## 一、评审概述
【2-3句话概括整体评审结论，说明本次评审覆盖的代码范围、整体合规情况、核心问题数量与总体质量判断】

## 二、修改建议
### 问题1（严重/高/中/低）
**问题说明**：【标准要求是什么，实际代码如何偏离，具体错在什么位置】
**涉及文件**：【精确到文件路径，可补充具体函数/行号】
**修改思路**：【具体、可执行的调整方向】

### 问题2（严重/高/中/低）
...
```

## 实操要点

- **先看 `git diff` 再看文档，还是先看文档再看 `git diff`，两者要交叉验证。** 单看 diff 容易只发现代码质量问题而忽略需求/设计层面的偏差；单看文档不看实际代码变更，则可能引用已经不存在的旧代码路径。两者结合才能定位真实偏差。
- **超范围实现是高优先级问题，即使代码质量很好。** 哪怕多做的那部分代码写得无可挑剔，只要不在需求和设计范围内，就要按"高"或以上级别记录，因为这类改动会带来未经评审的行为变化和维护负担。
- **测试完备性审查要实际运行测试，不能只读测试代码判断"看起来覆盖了"。** 读代码可能会漏掉断言写错、测试实际没有跑到目标代码路径等问题。
- **精确定位到行号需要先读一遍变更文件的实际内容**，不要凭 diff 摘要猜测行号——diff 里的行号和文件当前实际行号可能因为其他改动而错位，要用 Read 工具核对当前文件确认准确位置。
- **问题数量不是评审质量的指标。** 找到 3 个精确、可执行的高价值问题，好于列出 10 个模糊或次要的问题。宁可精简，不要为了显得"评审很认真"而拼凑问题。
