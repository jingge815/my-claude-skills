# 代码评审报告工具

以需求文档、设计文档、实施文档为唯一基准，审查调用方指定的 Git 变更范围（默认是工作区未提交的改动，也可以是指定提交区间），判断实现是否忠实对齐了这三份文档，并把发现的问题按严重性分级整理成一份精简、可直接拿去改代码的评审报告。

这个技能的定位是"合规校验"，不是"代码美化建议"。它不会因为看到一段代码写得不够优雅就提出改进意见——除非那段代码违反了需求、设计，或者项目已有的编码规范。个人偏好、设计外的优化想法，都不属于本技能的评审范围。

## 何时使用本技能

用户已有对应的需求文档、设计文档、实施文档，并且项目里有待评审的 Git 变更代码（未提交改动，或调用方指定的提交区间），想知道这些变更是否忠实执行了文档要求。典型场景是 `tdd-implement` 技能跑完之后，在提交代码前做一次独立校验；用户自己手写了代码想验证是否跑偏；或者要回溯评审一段已经提交的改动。

如果三份文档中有缺失（比如只有需求没有设计），要先向用户确认能否评审——没有设计文档就无法判断"设计符合度"这一维度，此时应明确告知这一维度无法评审，而不是跳过不说。

## 不可违背的原则

1. **评审依据唯一。** 所有问题判定必须能追溯到需求文档、设计文档，或项目现有的编码规范（如 CLAUDE.md、lint 配置、既有代码风格）。不能引入个人偏好或者"我觉得这样更好"的设计外优化建议。
2. **只评审调用方指定的变更范围。** 调用方给了提交区间时用 `git diff base..head` 确定范围，并叠加 `git diff HEAD` 的工作区未提交改动；没给区间时用 `git status`/`git diff` 只看工作区和暂存区里尚未提交的改动。只针对该范围内的改动（新增、修改、删除的文件）发表意见，不对范围外早已存在的代码做评审。
3. **问题描述必须三要素齐全：标准是什么、实际是什么、错在哪里。** 禁止"这段代码逻辑不太对"这种模糊定性，必须写清楚文档/规范要求的是什么，代码实际做了什么，两者之间的具体偏差点；并追到问题的根本原因——是哪个设计缺陷、缺失的约束或错误假设导致了它，同一根因还可能影响哪些代码路径。
4. **严重性分级刚性排序。** 所有问题按"严重 > 高 > 中 > 低"从上到下排列，影响功能正确性、偏离需求或设计核心的问题必须排在前面。
5. **报告保留问题清单与修改建议、核心目标完成情况和验证边界。** 不写无关背景、表扬或通用方法论。未发现问题时如实说明，但仍须逐条判断核心目标是否完成，并说明证据与未验证范围；未发现问题不等于全部验收通过。
6. **只评审不修改、不做实现决策。** 给出修改思路即可，不直接改代码；如果一个问题有多种合理的修改方式，把方向说清楚，选择权交给开发者。修改思路必须针对根本原因、能从根本上消除这类问题，而不是只让当前个例不再出错；只打补丁的建议视为不合格。根因如果出在设计文档本身，明确指出这是设计层面的问题、需要回到设计确认，不要自行提出设计外的方案。
7. **文档表达遵循“文档表达规范”。**

## 四个评审维度

对每一处变更，都要从以下四个维度逐项校验：

1. **需求一致性**：这段改动是否在需求文档划定的范围内？是否存在需求要求但代码未实现（遗漏），或代码实现了需求之外的功能（超范围）？
2. **设计符合度**：代码的模块划分、接口定义、数据结构是否与设计文档一致？如果设计文档指定了某个函数签名、某种流程，代码是否照做？
3. **代码质量**：逻辑正确性、异常处理是否完整、边界条件是否覆盖；是否遵循最小改动原则（有没有不必要的新增类/方法/依赖、无关的重构）；注释是否符合规范（仅关键逻辑加 1-2 句中文注释，无中英文混杂的口语化表达，无冗余注释）。
4. **测试完备性**：是否遵循 TDD（有实现必须有对应测试）；测试是否真的覆盖了对应功能的正常场景和关键边界场景；是否存在测试与代码实际行为不匹配的情况（测试断言的和代码做的不是一回事）。

## 文档表达规范

正文以连贯段落解释原因与机制，全文围绕核心目标组织；章节先总述再展开。图表前说明目的与阅读重点，图后仅补充关键机制或结论，不逐项复述。参数与日志字段对照可用表格，操作步骤可用编号列表，命令使用代码块，不为“段落为主”而将对照信息强行写成长段落。

正文自然段以两个全角空格（两个 U+3000）开头；标题、表格、代码块和列表标记行不缩进。使用准确、连贯的中文，代码标识符与技术专有名词保留原文；实现结论以实际阅读过的代码为依据，验证结论按证据状态表述。

## 标准工作流程

### 阶段一：输入接收与基线对齐

- 接收需求文档、设计文档、实施文档的路径（或按标识在 `docs/` 目录下查找同一需求标识的三份文档）。
- 确定本次评审的代码范围，列出所有新增、修改、删除的文件：
  - 调用方给了提交区间：用 `git diff <base>..<head>` 看已提交区间，再叠加 `git diff HEAD`（包含已 staged 和未 staged 的工作区改动）。
  - 没有区间：用 `git status` 和 `git diff`（包含已 staged 和未 staged 的改动）。
- 从三份文档中提取评审基准：需求范围与验收标准、设计文档的模块/接口/数据结构定义、实施文档记录的任务清单与预期改动文件。
- 如果评审范围内没有任何变更，直接告知用户，不要凭空评审。

### 阶段二：合规性与一致性审查

- 逐个变更文件核对：这个改动对应设计文档里的哪个任务/模块？如果对应不上，判断是遗漏记录还是超范围实现。
- 检查是否有需求文档要求但本次变更中完全没有涉及的功能点（可能是漏做，也可能是分批提交中的一部分——如果实施文档显示这是有意分阶段的，就不算问题）。
- 检查是否存在设计文档之外的功能实现、无关的重构或代码优化（哪怕代码本身写得更好，只要设计没要求，就是超范围）。
- 检查最小改动原则的执行情况：有没有可以复用现有代码却重新写了一遍的地方，有没有为了这次改动引入了不必要的新依赖。

### 阶段三：代码质量与测试审查

- 对变更代码逐行/逐块审查逻辑正确性，重点看条件分支、循环边界、空值/异常处理是否完整。
- 核对注释规范：关键逻辑和复杂分支是否有恰当的中文注释（不超过两句话），是否存在解释"做了什么"而非"为什么"的冗余注释，是否有中英文混杂的表达。
- 核对是否每个新增/修改的功能点都有对应测试，测试是否真的会在功能被破坏时失败（而不是形式上存在但断言很弱）。
- 先核对已有验证证据的来源、代码基线和环境；相关代码与环境适用条件未变时复用。代码发生相关变化、证据缺失或不足以判断问题时，仅补做必要验证，不默认重跑全量回归。证据统一标为“本次实际验证”“复用已有验证”或“仅核对实现但未执行”；最后一类不能据此宣称测试通过。

### 阶段四：问题整理与报告生成

- 汇总发现的所有问题，按"严重 > 高 > 中 > 低"排序：
  - **严重**：功能不正确、会导致数据错误或系统故障、完全偏离设计核心方案
  - **高**：明显超出需求/设计范围、关键测试缺失、破坏了现有功能
  - **中**：设计细节不符（如接口参数命名/顺序不一致）、边界场景遗漏、非核心逻辑的注释/规范问题
  - **低**：轻微的规范性问题（如注释风格轻微不符），不影响功能和后续维护
- 每个问题写清楚：问题说明（标准+实际+偏差点）、根本原因（为什么会发生、同一根因还影响哪些位置）、涉及文件（精确到路径，尽量给出函数名/行号）、修改思路（具体可执行、针对根因，能同时消除同类问题）。
- 按下方固定模板生成报告，文件命名为 `docs/review-<需求简称或唯一标识>-<YYYYMMDD>.md`，标识沿用需求/设计/实施三份文档已经使用的标识，保持四份文档可追溯。
- 如果没有发现任何问题，评审概述里明确写"本次评审未发现需求、设计、代码质量、测试完备性方面的问题"，「二、修改建议」一节写"无"，不要编造问题凑数。

## 实操要点

- **先看 `git diff` 再看文档，还是先看文档再看 `git diff`，两者要交叉验证。** 单看 diff 容易只发现代码质量问题而忽略需求/设计层面的偏差；单看文档不看实际代码变更，则可能引用已经不存在的旧代码路径。两者结合才能定位真实偏差。
- **超范围实现是高优先级问题，即使代码质量很好。** 哪怕多做的那部分代码写得无可挑剔，只要不在需求和设计范围内，就要按"高"或以上级别记录，因为这类改动会带来未经评审的行为变化和维护负担。
- **测试结论必须有执行证据。** 可以复用基线与环境适用的已有结果；证据不足时补做必要验证，不能仅凭阅读测试代码宣称测试通过。
- **精确定位到行号需要先读一遍变更文件的实际内容**，不要凭 diff 摘要猜测行号——diff 里的行号和文件当前实际行号可能因为其他改动而错位，要用 Read 工具核对当前文件确认准确位置。
- **问题数量不是评审质量的指标。** 找到 3 个精确、可执行的高价值问题，好于列出 10 个模糊或次要的问题。宁可精简，不要为了显得"评审很认真"而拼凑问题。
- **只打补丁的建议不算合格。** 如果一处空值判断缺失反映的是整层调用缺少统一的输入约束，修改思路就应落在约束的统一定义与校验上，并列出同一根因影响的其他位置；只在报错的这一行加一个 `if`，只是让当前个例不再出错，并没有消除问题。
- **优先围绕需求文档中的核心指标展开评审，要给出核心目标是否完成的结论。**
- **可读性是评审报告的核心价值。** 读者可能是开发者、测试人员、项目经理，甚至是甲方的技术负责人。报告要让他们一眼就能看懂问题和修改方向，而不是让他们去猜测你的意思。杜绝中英文混合，除非英文专有名词，杜绝口语化表达，杜绝冗余注释。
