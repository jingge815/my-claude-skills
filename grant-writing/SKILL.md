# 科研基金申请书全流程撰写助手（多 agent 编排版）

辅助纵向/横向科研项目申请书从调研到成稿的全过程。适用前提是用户已经有项目主题，或已有前期开发基础、研究思路、源码与技术文档。没有主题时先问主题，不凭空立项。

这个技能要解决的核心问题只有一个：申请书看起来像在"做系统、搭平台"，而评审要看的是"解决什么科学问题、用什么方法、克服了现有方法的什么原理性缺陷"。平台、软件栈、系统只是研究成果的验证载体，不是研究本身。

## 编排模型：主 agent 调度，子 agent 执行

本技能的文档量大、流程长，单个对话上下文装不下全过程。**主对话（你）不亲自写正文、不亲自画图、不亲自校对、不亲自构建 docx**，只做四件事：读交接物、跑机械校验、决定进入下一阶段还是返工、向用户汇总。每个阶段派一个子 agent 执行（Agent 工具），子 agent 之间只通过落盘文件交接，不通过主对话转述。

| 主 agent 要做 | 主 agent 不做 |
| --- | --- |
| 读规范文件（本目录 `references/`）并写成子 agent 的 brief | 把子 agent 的完整产出读进上下文（只读摘要 + 机械校验结果） |
| 派发子 agent、等待回报、核对交接物存在且达标 | 自己起草或润色申请书段落、自己调图坐标、自己逐句校对 |
| 每阶段末跑 `scripts/check_md.py` 等机械校验，看退出码 | 凭印象判断"差不多可以了" |
| 把阶段结果、遗留问题、需要用户决策的事项汇总给用户 | 跳过门禁把带病的产物带进下一阶段 |

子 agent 的 brief 怎么写、有哪些子 agent 角色、交接物协议、异常处理，见 `references/orchestration.md`。**派任何子 agent 之前先读它。**

## 何时使用本技能

用户要产出一份可申报的申请书正文，或要先做支撑这份申请书的调研。典型输入是：项目主题，加上可选的前期基础、目标基金类别、指定模板、字数要求。

以下情况不用本技能，改走对应技能，本技能不代做：

- 用户只要一份带引用的技术调研报告、不进入申请书写作 → 调用 `claude-skills-research`。
- 用户只要把一份模板的排版抽成可复用的格式子技能 → 调用 `format-replica-skill-gen`。
- 用户要的是需求文档、技术设计、代码实现 → 分别调用 `requirement-doc`、`tech-design-doc`、`tdd-implement`。
- 用户已有一份申请书只要转答辩 PPT → 调用 `proposalword2ppt`。

本技能只新增、只维护 `grant-writing/` 这一个技能目录，不修改上述任何技能的文件。配合方式是在阶段 2、阶段 4 调用它们，见「配合调用的技能」。

## 不可违背的原则

1. **研究性重构。** 禁止把"实现 XX 功能、搭建 XX 平台、开发 XX 系统"当作研究内容来写。改写成"研究 XX 机制、建立 XX 方法、构建 XX 模型、揭示 XX 规律"，平台只出现在验证环节，作为成果载体之一。判断标准：删掉所有系统名和平台名之后，这段话是否仍然在讲一个研究问题。如果删掉之后什么都不剩，这段就是工程描述，必须重写。
2. **一一对应。** 研究现状里提炼出的每一条核心不足，都必须在研究内容里有且仅有一个对应的解决条目；技术路线逐条支撑研究内容；预期成果逐条支撑研究目标。对应链的两端要顶到科学问题和传统方法原理：每条不足由某条传统方法的原理性限制推出，并指向关键科学问题的某个成分；关键科学问题的每个成分都有不足支撑、都有本文方法的机制回应。写完后要能画出一张「传统方法原理 → 不足 → 科学问题成分 → 本文方法机制 → 此前做不到、现在能做到的事」的对照表，对不上的环节要么补上，要么删掉。
3. **原理层创新。** 创新点必须落到方法原理：现有方法的原理是什么、这个原理决定了什么固有缺陷、本方法的原理是什么、它凭什么能克服那个缺陷。只对比"我们多了某功能、性能更好"不算创新论证。
4. **先有证据再下笔。** 研究背景和现状必须来自实际检索到的文献、政策文件或用户提供的素材，不凭记忆编造。研究内容和技术路线必须来自用户的源码、技术文档或已确认的研究思路；用户没给素材又没确认思路时，停下来问。引用的每一条都要打开核对过题名、作者、年份、出处，并且**全文精读**。外部可核验的数字要用声明口径现场重数；转述数字不得直接引用；核对发现原文无此数据时立即弃用，不换一个相近数字继续写。PDF 下载不了时把题单列清单告知用户，由用户获取后入库再继续，不得用摘要、落地页或二手转述顶替全文。
5. **需求导向精读。** 每篇拟引用论文的精读记录不是论文摘要的复述，而是「围绕申请书需要什么」的提炼：它服务于哪条论断、提供哪个可引用事实、原理层局限是什么、不引用它会怎样。写不出「不引用会怎样」的论文不进正文。
6. **站位先高后落。** 课题意义的顺序固定为：国家或行业的重大需求 → 该需求在技术上卡在哪里 → 这个技术卡点背后的科学问题 → 本课题为什么现在必须做。禁止开篇就堆技术细节。需求优先用行业事实和量化数据立起来，政策只在问题收束处作一句佐证，全篇政策直接引用不超过两处。
7. **口径唯一。** 摘要、研究目标、研究内容、预期成果、进度安排里的论文篇数、原型套数、报告份数、指标数值必须逐字一致。任何一处改了数字，其余所有出现处在同一次修改里一起改。
8. **成果写可达成的。** 预期成果和考核指标是将来验收的依据。没有把握完成的指标要降级、改成定性或模糊表述，并注明降级原因。区分功能验证、仿真估计、代理预测、真实硬件实测四类证据口径，没有实测数据支撑的不得写成实测结论。
9. **格式服从模板。** 用户给了模板，章节划分、标题层级、字数、是否允许分点，全部以模板为准，本技能的默认结构只是没有模板时的兜底。模板要求"单段连贯、禁止分点"时，正文就不得出现条列。
10. **风险写成可控可克服的。** 风险分析的目的是让评审相信项目做得成，不是展示项目有多难。每条风险都必须配「控制手段 + 兜底方案 + 不影响总体目标」三件套；后果措辞用可识别、可度量的过程描述，不用「失败、不收敛、崩溃」这类裸词。
11. **不照搬范本。** 用户提供的历史申请书、兄弟课题申请书、写作提示词，只作为写法参照。不得把其中的技术路线、指标数字、章节数量照抄进新申请书。借鉴的是论证链条，不是内容。
12. **图是画出来的，不是拼出来的。** 最终稿里禁止 ASCII 框图、禁止用代码块冒充图。每张图由专职画图子 agent 先生成 PNG、经过机械审计与视觉自检至少两轮通过后，再由写手嵌入。

## 标准工作流程与阶段索引

严格按阶段推进。上一阶段的产物未落盘、门禁未过、未给用户确认，不得进入下一阶段；例外是阶段 6——它紧随阶段 5 成稿自动执行。每个阶段一个子 agent 执行，主 agent 调度。**派子 agent 前读对应阶段的规范文件。**

| 阶段 | 执行者（子 agent） | 输入 | 落盘产物 | 规范文件 | 进入下一阶段的门禁 |
| --- | --- | --- | --- | --- | --- |
| 1 研究问题拆解与框架锚定 | 拆解员 | 主题 + 用户素材 | `01-调研大纲.md` | `references/stage-1-outline.md` | 七槽位齐全、闭环句式写出、用户确认大纲 |
| 2 文献调研与需求导向精读 | 调研员（检索）+ N 个精读员（分片并行） | 调研大纲 | `02-资料库/`（pdfs、texts、index.md、阅读记录、精读记录、待补全文.md、背景数字核验.md） | `references/stage-2-research.md` | 全文 ≥81 篇、每篇有阅读记录、拟引用篇有需求导向精读记录、`待补全文.md` 清空或用户豁免 |
| 3 三案竞标与调研论证 | 3 个竞标写手（并行）→ 主 agent 或裁判选优 → 论证员 | 调研大纲 + 资料库 + 用户素材 | `03-竞标-案A/B/C.md`、`03-方案竞标.md`、`03-调研论证.md` | `references/stage-3-bid-argument.md` | 三案槽位齐全且建立资料库编号、五条标准逐案评语落盘、基准案唯一、论证六章齐全 |
| 4 确认写作格式 | 格式员 | 用户模板或四问答复 | `04-格式说明.md` | `references/stage-4-format.md` | 章节层级、字数、是否分点、图表位置、参考文献格式均可执行；用户确认 |
| 5a 提炼已有工作 | 提炼员 | 源码、技术文档 | `05-已有工作提炼.md` | `references/stage-5-writing.md` | 每模块入口/数据对象/依赖/可检查物四件事齐全 |
| 5b 撰写正文（不含图） | 写手 | 论证 + 格式说明 + 提炼 + 精读记录 | `05-申请书.md`（图位留 `![](figs/figN.png)` 占位与图规格）、`05-口径表.md` | `references/stage-5-writing.md` + `references/writing-rules.md` + `references/writing-sections.md` | 正文各章写齐、`check_md.py --allow C03,C04,C18` 退出码 0 |
| 5c 专职绘图 | 画图员（每图可并行） | 写手的图规格 + 正文相关段 | `figs/figN.spec.json`、`figs/figN.png`、`figs/figN.png.audit.txt` | `references/figures.md` | 每图 `draw_figure.py` 审计全 PASS、画图员视觉自检 ≥2 轮、写手核对图内术语与正文一致后嵌入 |

## 质量门禁（主 agent 在阶段 6 与每轮修订后必须跑）

```bash
PY=~/.claude/skills/grant-writing/.venv/bin/python
S=~/.claude/skills/grant-writing/scripts
$PY $S/check_md.py    grant-<简称>/05-申请书.md --json grant-<简称>/scripts/check_md.json   # 机械校验 C01–C20；阶段 5b 门禁加 --allow C03,C04,C18
$PY $S/build_docx.py  grant-<简称>/05-申请书.md --out grant-<简称>/05-申请书.docx [--template 模板.docx]
$PY $S/verify_docx.py grant-<简称>/05-申请书.docx grant-<简称>/05-申请书.md [--allow-prefix N]  # docx 结构回归
```

三个脚本任一退出码非 0，不交付。机械校验只覆盖可脚本化的部分；内容级审查（九条验证点、文字校对）由子 agent 按规范文件执行，主 agent 核对其落盘记录，不替它做。

## 实操要点

- **先读素材再检索。** 用户给了源码和技术文档时，先做成 `05-已有工作提炼.md`，研究内容与技术路线只从这份提炼里取机制和数据对象，文献只用于背景和现状。
- **借鉴写法不借鉴内容。** 参照其他申请书时，学习它"问题—证据—缺口—方法—验证"的连续论证，不搬它的章节数量、技术名词和指标。
- **数字全部进一张表。** 论文篇数、原型套数、指标值在动笔前列成 `05-口径表.md`，后文从这张表取数。
- **委派一切，核验一切。** 检索、写案、写正文、画图、校对、构建全部委派给子 agent；主 agent 对每一项交接物只做两件事：跑脚本看退出码、抽查指定段落核对原文。
- **模板的形式约束高于本技能的默认结构。** 本技能里的章节划分只在没有模板时使用。

## 配合调用的技能

本技能是编排者，下面两个技能是被调用的现成能力。调用时只读它们的 `SKILL.md` 并按其流程执行，不修改它们的任何文件。

| 阶段 | 调用 | 它负责 | 本技能保留的部分 |
| --- | --- | --- | --- |
| 阶段 2 | `claude-skills-research` | 学术文献的检索、来源准入、原文核验、正式引用 | 资料库落地（PDF、仓库、政策文件）、需求导向精读、和调研大纲的对应关系 |
| 阶段 4 | `format-replica-skill-gen` | 从用户模板抽取形式、生成格式复刻子技能 | 把子技能收敛成 `04-格式说明.md`，并据此写正文 |
| 阶段 5 及之后 | 无 | — | 正文、图、校对、docx 全部由本技能的子 agent 完成 |

`requirement-doc`、`tech-design-doc`、`tdd-implement` 不在本流程内。用户的请求如果其实是需求、设计或编码，直接改走对应技能。
