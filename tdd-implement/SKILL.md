# TDD 实施执行工具

把一份已经定案的设计文档，严格、忠实地转化为可运行的代码，全程用测试驱动开发（TDD）作为纪律约束，并输出完整可追溯的实施记录；如果之后出现了针对这次实施的评审文档，还要负责把评审问题逐条确认、逐条修复，并把结果更新进同一份实施文档。

这个技能的核心价值是"执行纪律"：不引入设计之外的想法，不跳过测试直接写实现，不为了图省事扩大改动范围。它不是一个"顺便优化一下"的工具——发现设计有问题就如实记录反馈，而不是自己动手"顺便"改掉。修复评审问题时同样如此：只修评审文档里指出的问题，不借机夹带其他改动。

## 何时使用本技能

用户已有需求文档和设计文档（一般来自 `requirement-doc` 和 `tech-design-doc` 两个技能的产出，或用户自己准备的等价文档），现在要把设计落地成代码。使用本技能而不是直接手写代码，尤其是当用户强调"按设计来"、"别加东西"、"要写测试"的场景。

如果设计文档还不存在或不完整，先引导用户去用 `tech-design-doc` 技能补上，不要在设计缺失的情况下"边设计边实现"。

如果本次实施完成后，项目里又出现了一份或多份 Git 未提交的评审文档（一般来自 `code-review-doc` 技能的产出，命名为 `docs/review-xxx-YYYYMMDD.md`），本技能也负责处理："根据评审文档改一下""评审提的问题修一下"等场景，详见下方阶段五。

实施文档是过程记录，不是最终交付文档。设计原理、总体流程图等面向读者的内容由 `techdoc` 技能在全部工作结束后基于最终代码撰写，本技能只负责把它需要的素材（实施问题、偏差、验证命令与结果、遗留问题）如实记录下来，不在实施文档里写原理和流程图。

## 不可违背的原则

1. **设计文档是编码的唯一依据。** 只实现设计文档（及其对应的需求文档）里写明的内容，绝不新增设计外的功能、绝不做设计外的重构或优化，即便你看到"顺手就能改好"的代码异味，也只能记录下来反馈，不能动手改。
2. **TDD 是刚性流程，不是建议。** 每个任务单元必须先写测试、运行确认失败，再编码实现，再运行确认全部通过——顺序不能颠倒，不能跳过"先看到测试失败"这一步（否则无法验证测试本身是否有效）。当前任务单元测试未全部通过，不允许开始下一个任务单元。
3. **最小改动原则。** 优先修改和复用现有代码、现有函数、现有依赖，不引入不必要的新类、新方法、新依赖。代码增量严格控制在满足设计所需的最小范围，不做"顺便"的抽象或泛化。
4. **注释要精简且是中文。** 只在关键逻辑、复杂分支处加注释，每处不超过两句话，用中文表达，专有名词（如库名、协议名）保留英文原文，禁止中英文混杂的口语化写法，禁止解释"做了什么"（代码本身已经说明），只在必要时解释"为什么这样做"。
5. **遇到偏差只记录、不擅自决策。** 如果设计与现有代码冲突、设计描述有遗漏或模糊到无法直接编码，立即停下记录问题，向用户反馈确认，不自行推断设计意图、不擅自调整方案、不绕过冲突硬编。
6. **完成的判定标准是刚性的三条同时满足：** 设计文档所有任务项 100% 覆盖、对应测试全部通过、全量回归无新增失败。三者缺一都不能标记为"已完成"。
7. **评审问题必须先确认、再修复，且要全部修完。** "确认"指实际验证问题是否真实存在（读代码、复现现象，必要时先写一个能复现问题的失败测试），不是照抄评审文档的结论就算确认。确认为真的问题必须逐条修复，不能只挑容易的改、遗漏其余；确认后判断为不成立的问题要记录不修复的理由，不能不声不响地跳过。每条问题的修复同样要走"先写测试、测试失败、改代码、测试通过"的循环，不能因为是"修复"就绕开 TDD 纪律。修复必须落在根本原因上：先查清问题为什么会发生、同一根因还影响哪些代码路径，再在根因处做最小但完整的改动，使同一类问题不再复发；只针对评审点名的个例打补丁、换个入口仍会出错的修复不算完成。同一根因导致的同类问题即使评审未逐条点名，也属于该条修复范围；与根因无关的改动仍不得夹带。若根因出在设计层面，按原则 5 先向用户确认，不自行扩大实现范围。

## 文档表达规范

正文以连贯段落解释原因与机制，全文围绕核心目标组织；章节先总述再展开。图表前说明目的与阅读重点，图后仅补充关键机制或结论，不逐项复述。参数与日志字段对照可用表格，操作步骤可用编号列表，命令使用代码块，不为“段落为主”而将对照信息强行写成长段落。

正文自然段以两个全角空格（两个 U+3000）开头；标题、表格、代码块和列表标记行不缩进。使用准确、连贯的中文，代码标识符与技术专有名词保留原文；实现结论以实际阅读过的代码为依据，验证结论按证据状态表述。

## 标准工作流程

### 阶段一：输入接收与任务拆解

- 接收需求文档、设计文档，以及用户指定或设计文档中已经写明的代码改动范围。
- 开始改代码前，记录起始基线：当前分支名与 `git rev-parse --short HEAD`，写入实施文档头部的"起始基线"。工作区已有未提交改动时一并注明，后续统计本需求改动范围以此为起点。
- 把设计文档"代码改动清单"一节拆解为独立可执行的任务单元，每个任务单元对应设计里的一个具体改动点（一个文件/一个函数/一个接口级别的粒度，不要把整个模块揽成一个任务单元）。
- 按设计文档标注的优先级（继承自需求的 P0/P1/P2）给任务单元排序。
- 读一遍现有代码，初步核对设计与代码现状是否匹配——如果设计文档假设的代码结构已经不存在，或者设计里提到的接口签名和实际代码不一致，这里就要发现并先记录下来，不要留到实施中途才发现。
- 如果发现设计文档本身有明显缺失（比如某个任务点没有说清楚验收标准，无法判断测试该怎么写），停下来向用户确认，不要靠猜测继续拆解。

### 阶段二：TDD 循环实施（逐个任务单元执行，严格按顺序）

对每一个任务单元，严格执行以下五步，不得跳步、不得合并步骤：

1. **编写测试**：针对当前任务单元编写单元测试或功能测试，覆盖正常场景和关键边界场景（至少包含一个正常路径和一个边界/异常路径，除非设计文档的验收标准明确只要求正常路径）。测试要写在项目现有的测试框架和目录结构下，不引入新的测试框架。
2. **验证失败**：运行这个测试，确认它当前是失败的。如果测试意外通过了，说明测试用例本身没有正确覆盖待实现的行为，需要重新设计测试，不能带着一个"假阳性"的测试往下走。
3. **编码实现**：严格按设计文档进行代码修改或新增，优先在现有函数/类/模块上做最小修改。关键逻辑或复杂分支处最多加两句中文注释。这一步只做能让当前测试通过、且在设计范围内的改动，不夹带其他改动。
4. **验证通过**：运行测试，确认全部通过。不通过就回到第 3 步调整代码（不是调整测试来迎合代码，除非发现测试本身有错）。全程不引入设计外的功能。
5. **记录状态**：记录这个任务单元的完成状态、具体改动的文件和函数位置、执行的测试命令原文、测试用例名与结果，作为阶段四文档的原始素材。同时检查本任务单元是否出现以下情况，有则当场写入"实施问题记录"（问题、根因、解决方案、实现位置、验证用例）：
   - 根因不显然，需要读代码或调试才查清的问题；
   - 设计文档没有预料到的边界场景或代码现状；
   - 存在多种做法、需要取舍的实现点（取舍若偏离设计，按原则 5 先向用户确认，并同时记入"偏差说明"）。
   拼写修正、常规增删字段这类琐碎改动不记入。

只有当前任务单元的测试全部通过，才能进入下一个任务单元。

### 阶段三：全量回归与校验

- 所有任务单元完成后，运行项目里全部相关的测试（不只是新增的测试），确认没有引入回归问题。
- 逐项核对设计文档里的所有改动项，确认每一项都能对应到一个已完成的任务单元——不多不少，既没有遗漏，也没有做了设计里没写的事。
- 如果回归测试发现问题，回到阶段二修复，不要带着已知的回归问题进入文档输出阶段。

### 阶段四：实施文档输出

- 用户确认实施完成（或者当前范围内的任务已全部走完 TDD 循环）后，按下方固定模板生成实施进展文档。
- 文件命名固定为：`docs/implement-<需求简称或唯一标识>-<YYYYMMDD>.md`，简称和标识沿用需求文档/设计文档里已经使用的标识，保持三份文档命名一致，方便追溯。若当天已经生成过同一标识的实施文档，直接在原文件上更新，不要另外创建一份新文档。
- 文档要如实反映实施结果：如果只完成了部分任务，「实施结论」就写"部分完成"，并在"问题与偏差说明"里说明原因，不要为了让文档看起来完美而美化结果。
- 文档注意篇幅,不写后续文档模板没有提到的其他内容,语言准确,通俗易懂,禁止中英文混合,除非英文专有名词。
- 文档表达遵循下方“文档表达规范”。

### 阶段五：评审问题确认与修复（存在 Git 未提交的评审文档时触发）

本阶段在阶段四之后、或者在已有实施文档的基础上被重新触发——典型场景是 `code-review-doc` 技能已经产出评审文档，用户要求"照评审改一改"。

1. **收集评审文档**：用 `git status` 找出所有 Git 未提交的 `docs/review-<同一需求标识>-*.md` 文件。如果同一标识有多份，只读取最新的一份（按文件名日期判断，日期相同时按修改时间），并在修复记录中注明本轮依据的是哪一份。把该文档中的问题按严重性排序（严重 > 高 > 中 > 低）整理成问题清单。
2. **逐条确认问题**：对清单上的每一条问题，实际验证是否成立——读评审文档指出的文件和位置的当前代码，判断评审所述的"标准 vs 实际"偏差是否依然存在（代码可能在评审之后已经变化）。确认方式优先是"能否写出一个复现问题的测试"：如果能写出一个当前会失败的测试，问题成立；如果读代码后发现问题已不存在或评审描述有误，记录为"不成立"及理由，不修复。确认成立时同步定位根本原因，记录问题为什么会发生、同一根因还影响哪些同类路径，作为修复方案的依据。
3. **逐条修复已确认的问题**：对每一条确认成立的问题，按严重性从高到低依次处理，每条问题独立走一次完整 TDD 循环（写测试→验证失败→改代码→验证通过）。测试除覆盖评审点名的场景外，还要覆盖同一根因下的其他触发路径；改代码要落在根因处（统一的约束、接口、默认值或错误处理等），而不是在每个出错位置分别加补丁。只修这一条问题的根因范围，不夹带无关改动；同一根因的同类问题即使评审未逐条点名，也一并修复并在记录中注明。同一文件涉及多条问题时，改动也要能拆分清楚对应到各自的问题编号。
4. **全部修复后回归**：所有已确认问题修复完，再跑一次项目全量测试，确认修复没有引入新的回归，记录命令原文与结果数字。
5. **更新实施文档**：不新建文档；先通读已有的 `docs/implement-<需求标识>-<YYYYMMDD>.md`，再按文末"多轮更新规则"在既有章节上就地修改，禁止整段追加。修复过程中如果出现符合阶段二第 5 步标准的问题，同样写入"实施问题记录"；修复关闭了某条已知问题或待确认事项的，同步把对应条目的状态改为"已关闭"并写明关闭说明。如果找不到对应的实施文档（比如实施文档已被删除或标识不一致），向用户确认后再决定是新建还是使用用户指定的文件。
6. **提示下一步**：评审问题全部处理完毕且全量回归通过后，提示用户可以使用 `techdoc` 技能生成最终技术文档；如仍有未修复问题，说明它们会作为遗留问题出现在技术文档中。

## 实操要点

- **任务单元切得细一点。** 一个任务单元对应"一个可以独立写测试、独立验证通过"的最小改动，不要把设计文档里的一整个模块当成一个任务单元去做，否则 TDD 循环形同虚设（测试写得又大又晚，失去了快速反馈的意义）。
- **测试框架跟随项目现状。** 先确认项目已经在用什么测试框架（看 `package.json`/`pyproject.toml`/`go.mod` 等或已有测试文件），沿用它，不要因为个人习惯引入新的测试工具链。
- **每完成一个任务单元就更新一次任务状态记录**（口头汇报或临时记录），不要等全部任务做完再回忆每一步的细节去凑文档——细节丢失会导致"改动详情"和"测试结果"写得笼统。
- **发现代码坏味道时的处理方式**：记录到"5.1 已知问题"里，写清楚具体位置和问题描述，在"关闭说明"中附上建议后续处理方式，但不要在本次实施里动手改，除非这正是设计文档要求的改动点本身。
- **和现有代码冲突时优先复用已有的相似实现。** 如果项目里已经有类似功能的模式（比如已有的校验函数、已有的错误处理封装），设计文档没有明确要求另起一套时，应该复用现有模式，这也是"最小改动原则"的一部分。
- **不要用"大致完成"糊弄验收标准。** 设计文档里如果给了可量化的验收标准（比如"响应时间小于200ms"），测试要真正验证这一点，不能只写功能性测试就宣称完成。
- **修复要治本，不要打补丁。** 修复前先问"这个错误为什么会出现、同一根因还会在哪些路径触发"：如果根因是某一层输入约定不统一，就在约定或入口处统一处理并排查所有同层调用点，而不是只在复现报错的那一行加判断。根治的范围限于同一根因，不等于可以顺手做无关重构。
- **"确认"是验证，不是复述。** 处理评审文档时，不能把评审文档里写的问题原样抄进修复清单就算完成确认，必须真正去读当前代码、能否复现，判断问题在当下是否依然成立——评审文档产出之后代码可能已经变化，评审文档本身也可能有误判。
- **评审问题清单按严重性顺序修，不要挑软柿子。** 多条问题存在时，先修严重和高优先级的，不要因为某条问题改起来容易就先改、把复杂的高优先级问题往后拖甚至遗漏。
- **多份评审文档以最新的一份为准。** 同一需求存在多份未提交的评审文档时，以最新的一份为准，不要把旧文档里的问题再处理一遍；修复记录里注明本轮依据的是哪一份文档。
