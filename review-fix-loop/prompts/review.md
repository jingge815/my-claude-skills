请使用 code-review-doc 技能，按技能中的流程与模板，对需求标识为 {req_id} 的 Git 代码改动做一次评审。

本次评审的仓库与改动范围见文末固定约定中的「评审范围」：配了 base 的仓库评审 base..head 的已提交区间加上当前工作区未提交改动；没配 base 的仓库评审未提交改动（git status / git diff HEAD / 未跟踪文件）。逐个仓库按该范围查看后合并评审：
{repos}

需求、设计、实施文档位于 {docs_dir}。

评审要求：
1. 每条问题先定位根因（为什么会偏离文档要求、同一根因还影响哪些入口和路径），再给出修改思路；修改思路要能一次性收敛同类问题，不能只针对单个探针或调用点给局部补丁。
2. 写入报告前用相反假设复核一次：换一条路径是否仍能绕过、是否会把合法路径误判；确认后再落笔。
3. 抽查前几轮已修复问题的根因与同类路径是否真正覆盖（可读历史 review 和实施文档的问题清单）；只在当时探针或单例上生效的，作为本轮问题列出并注明复发原因与完整修复范围。
4. 评审报告除问题清单外，必须单独回答需求文档的核心目标是否逐条完成（已完成/部分完成/未完成，附证据与缺口），并给出总体结论；只列代码问题不算完成评审。
5. 评审只跑确认本轮问题所需的最小测试，不重复跑修复方已跑且代码未变的测试，也不跑与本轮改动无关的全量回归；报告注明哪些证据是新跑、复用还是未跑。

证据统一标注为“本次实际验证”“复用已有验证”或“仅核对实现但未执行”。复用结果须记录来源、代码基线（含相关未提交改动）与环境并核对适用性；相关代码变化或证据缺失时仅补做必要验证，不默认重跑全量回归。操作示例与实测结果分开，未执行命令不得写成验证通过。
