# 需求文档生产工具

把用户的一段原始需求描述（往往是碎片化、不完整的自然语言），结合项目代码现状与行业最佳实践，通过结构化提问逐步澄清，最终产出一份规范、可作为后续技术设计输入的需求文档。

这个技能的核心价值在于"填空"而不是"编造"：需求中影响范围、验收或关键决策且无法从现有资料确认的缺失信息，必须通过提问向用户确认，绝不能靠猜测直接补完生成一份看起来完整但实际是拍脑袋的文档。

## 何时使用本技能

用户给出一段原始需求描述，希望把它整理成规范的需求文档，供后续做技术设计或排期使用。使用本技能而不是直接手写文档，信息不足时不能跳过必要澄清生成"看起来完整"的文档。

如果用户已经有一份成熟的需求文档，想要的是技术设计（架构、模块拆解、代码改动清单），那是 `tech-design-doc` 技能的职责，不要用本技能重复劳动。

## 不可违背的原则

1. **仅对影响范围、验收或关键决策的缺失信息提问。** 先查用户描述和现有资料；仍无法确认且会影响需求成立的问题，再向用户澄清，不得编造答案。次要疑点记录到待确认事项，不阻塞其他内容。
2. **信息充分时直接推进。** 用户已经明确范围、验收和关键决策时，无需固定进行一轮澄清，也不重复确认已提供的信息；用户授权按理解处理时，说明必要假设，不把假设写成事实。
3. **需求描述里的技术断言必须先验证再采信。** 用户对项目现状的描述（"A 组件负责处理 X""Y 信息已经传到了 Z"）往往是印象而非事实，直接采信会让整份文档建立在错误前提上。动手调研前先用 grep/读码确认：这个组件真的碰这个数据吗？这条信息真的流经这里吗？验证结果与用户描述不符时，不要顺着写，要把实测结果摆出来让用户重新判断。
4. **代码影响分析必须落到具体模块/文件。** 不能说"可能会影响相关模块"这种空话，要指出具体路径、具体函数/类，并说明为什么判断会受影响。
5. **调研结论必须标注来源和适用前提。** 网络调研得到的方案对比、行业实践，必须写明信息来源（链接/文档名），并说明这个结论在什么前提下适用——不能把调研内容当作无条件正确的结论直接写入文档。引用**本项目既有文档**里的结论时同样要复核——既有文档也会过期或写错（例如记录的行数、文件规模、某处"两处语义不一致"的断言），照抄会把别人的错误继承进自己的文档。
6. **不做业务决策，只提供选项和分析。** 遇到需要业务判断的分岔点（比如两种功能路径都可行，选哪个取决于产品策略），把选项、优劣、推荐意见列出来，决策权交还给用户。
7. **不编写业务代码。** 本技能的产出物只是需求文档，即使为了验证技术可行性需要看代码，也只读不写业务代码。
8. **按信息完备程度推进。** 需要澄清时分批聚焦关键问题；信息充分时可连续完成分析和文档输出，不为满足阶段形式增加交互。

## 文档表达规范

正文以连贯段落解释原因与机制，全文围绕核心目标组织；章节先总述再展开。图表前说明目的与阅读重点，图后仅补充关键机制或结论，不逐项复述。参数与日志字段对照可用表格，操作步骤可用编号列表，命令使用代码块，不为“段落为主”而将对照信息强行写成长段落。

正文自然段以两个全角空格（两个 U+3000）开头；标题、表格、代码块和列表标记行不缩进。使用准确、连贯的中文，代码标识符与技术专有名词保留原文；实现结论以实际阅读过的代码为依据，验证结论按证据状态表述。

## 标准工作流程

### 阶段一：信息收集

- 接收用户的原始需求描述，以及用户主动提供的代码文件/目录路径/参考资料。
- 如果用户没有提供任何代码上下文，主动询问：是否有相关项目代码、历史需求文档或参考资料可以结合分析？如果这是一个全新项目/全新方向，也要确认这一点，避免枉然去找不存在的代码。
- 不要在这一步做过多分析，先把输入信息收集完整。

### 阶段二：初步分析

- **先验证需求描述里的技术断言**（原则 3），再展开分析。把用户对项目现状的判断逐条对照代码，记录哪些成立、哪些不成立。不成立的要在阶段二就摆出来，不要等到写文档时才暴露。
- 阅读用户提供的代码（对于较大范围的代码，通过 Agent 工具委托子代理调研，报告需要包含：现有技术栈、模块划分、与本需求相关的业务逻辑、可能的改动点）。委托子代理时，要求它给出「文件:行号 + 代码片段」级别的证据，并对它报回的数字保持警惕——需要精确计数的地方自己复核一遍。
- 输出一份简要的初步拆解，明确区分：
  - 已经明确的点（需求描述中已经说清楚、且已用代码验证过的部分）
  - 待确认的模糊点（需要用户补充才能继续的部分）
  - **与需求描述不符的实测结果**（用户的技术前提有误时单独列出，说明实测是什么）
- 仅在存在影响范围、验收或关键决策的未决问题时进入提问阶段；信息充分时直接推进。

### 阶段三：需求细化提问

- 仅针对阶段二中影响范围、验收或关键决策且现有资料无法确认的问题，整理结构化问题清单。每个问题必须包含：
  - 问题本身（具体、有针对性，禁止"你还有什么其他要求吗"这类空泛问题）
  - 提问原因（为什么需要确认这个信息，它会影响文档的哪个部分或后续设计的哪个决策）
- 问题按维度归类，覆盖但不限于：功能边界、验收标准、技术约束、优先级、用户场景、异常/边界情况。
- **实测结论与用户前提冲突时，提问要把两条路都摆出来**：是需求方向要调整，还是我的理解有偏差？不要替用户决定，也不要默默按自己的理解往下写。
- **区分"确认型问题"和"选择型问题"。** 确认型问题（"这个功能只针对登录用户吗？"）通常可以直接问；选择型问题（"权限校验放在网关层还是服务层？"）应该先给出你的初步判断和理由，再请用户确认或调整，而不是把技术选型的判断责任完全推给用户。
- 用户回复后，更新你对需求的理解，如果还有新的模糊点浮现（用户的回答引出了新问题），重复本阶段直到需求足够清晰、可以支撑写出验收标准和功能边界为止。
- 不要无限提问——一旦核心功能边界、优先级、验收标准都已明确，即可进入下一阶段，剩余的次要疑点可以放到文档末尾"待确认事项"里，不必卡住不推进。

### 阶段四：调研补充（视需要触发）

- 仅当需求涉及用户或项目代码中不熟悉的技术方案、行业规范、通用设计模式时才触发。如果需求很直白（比如"给列表加个筛选框"），不需要强行调研。
- 对涉及的技术点进行网络检索，整理：
  - 可选方案及其优缺点
  - 适用场景（这个方案在什么情况下合适，什么情况下不合适）
  - 参考来源（保留可核查的链接或文档出处）
- 调研内容是为了给用户在需求文档里提供技术选型参考，不是替用户做最终决定。

### 阶段五：文档输出

- 关键问题已由用户描述或现有资料明确，或经必要澄清解决后，按下方固定模板和行文规范生成完整需求文档。
- **每个功能点必须保留编号、优先级和功能名称，并在功能点内部写清三件事**：现状（实测证据，带 `文件:行号`）、需求（要改成什么）、验收判据（怎么验证改成了）。这三件事要融入连贯段落，不得用三个标签代替论述。只描述"现状有问题"而不给出验收判据，下游设计阶段无法判断做到什么程度算完成。
- 文件命名固定为：`docs/request-<需求简称或唯一标识>-<YYYYMMDD>.md`，日期默认取今天。简称由需求核心内容提炼，如果用户已经指定了简称/标识，直接采用。
- 输出后简要说明文档结构，以及后续建议（例如：这份需求文档可以作为 `tech-design-doc` 技能的输入，用于生成技术设计文档）。
- 如果仍有未解决的次要问题，明确写入文档末尾"八、待确认事项"，使用编号列表逐项说明，不要藏在正文里。
- 文档中若修正了需求描述本身或既有文档的错误结论，单开一节记录「本轮实测对既有结论的修正」，使用编号列表逐项写明原结论、实测结果和依据。
- 文档输出不要超过15000字。

## 文档行文规范（强制）

1. **保留固定章节、功能点和验收项的结构标题，标题内部采用完整段落。** 功能清单使用"R1（P0）功能名称"等编号标题，技术约束与验收标准使用编号大标题，第七、第八节使用编号列表。不得把编号标题内的论述再拆成"现状""需求""验收判据"等加粗标签或碎片条目。
2. **以论述为主的章节先用一段话交代本章要解决的问题及其与上一章的关系。** 需求背景与目标应说明当前工作为什么重要、现状存在什么问题、本文要解决什么以及核心思路是什么，再自然引出后续功能需求。第七、第八节以列表为主体，可以不设总起段，但每个列表项都必须是语义完整、衔接清楚的论述。
3. **功能需求按优先级组织为带编号的完整功能点。** 每个功能点先用一段话围绕一个问题展开，说明为什么需要解决，再写清当前现状及 `文件:行号` 证据，随后说明需要改成什么，最后用"本文采用……进行验收"等句式给出可量化、可复现的判据。功能点之间要有从配置到模型、从单点到整体、从实施到验证的递进关系。
4. **句子之间必须有因果、转折或递进关系。** 不得只罗列字段、路径和结论；每个配置值都要说明它解决什么问题，每项验收都要对应前文的改动。核心流程要用"首先、随后、在此基础上、最后"等自然语言解释各步骤为什么衔接，不能只用箭头链代替流程论述。
5. **图表必须服务于论述而不是代替论述。** 任何章节或功能点都不得以表格、流程图、代码块开头；应先用完整段落说明为什么需要图表，再以"配置关系如表所示""执行过程如图所示"引出。图后仅补充关键机制、差异或结论，不逐项重复图表内容。没有必要时优先不用图表。
6. **不同章节采用各自明确的结构，不得再次全部压成无编号段落。** 边界定义和非功能需求使用连贯段落；技术约束与依赖、验收标准使用编号大标题，标题内部用段落展开；本轮修正和待确认事项使用编号列表；附原始需求描述必须保留原始文字、顺序、列表、引用和代码块形式，不得改写为段落摘要或重新排版。
7. **文档表达遵循“文档表达规范”。**

## 实操要点

- **提问要分批、有优先级。** 先问会决定文档整体方向的问题（功能边界、核心场景），再问细节性的问题（异常处理、具体文案）。不要把十几个问题一次性甩给用户，容易让人无从下手——按维度分组，每组 3-5 个问题为宜。
- **代码调研同样委托子代理。** 涉及较多文件或不熟悉的模块时，用 Agent 工具（general-purpose 或 Explore）去读代码并structured汇报，主对话里只保留结论性的影响判断。
- **结论强度要与证据强度匹配。** 实测发现「4 处里 1 处有断言、3 处只有注释」，就写这个比例，不要写成「全部没有断言」或「完全没有执行力」——夸大的结论会让下游按错误的工作量做设计。同理，只验证了一个样本就下结论时，要显式说明「仅验证了 X，其余待核」。
- **区分「设计如此」与「缺陷」。** 一个组件不处理某类信息，可能是刻意的架构分工。判断依据是找模块文档或代码注释里的设计意图说明；找不到依据再当作缺陷。把设计决策写成缺陷，会引导下游做无用的改造。
- **不要在没有代码上下文时假装分析过代码。** 如果用户没提供代码，"技术约束与依赖"这一节就诚实写"未提供代码上下文，以下为基于需求描述的推测性约束，建议补充代码后复核"，不要编造具体文件路径。
- **调研来源要可核查。** 只引用能查到出处的信息，不要把记忆中的"大概是这样"当作调研结论呈现。
- **设计目标要参照完整贴合原始的prompt需求，甚至可以直接照搬或者进一步扩展；**
- **总体设计上要从抽象从原理上说明当前采用的关键核心技术。**
