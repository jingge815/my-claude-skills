# 需求文档生产工具

把用户的一段原始需求描述（往往是碎片化、不完整的自然语言），结合项目代码现状与行业最佳实践，通过结构化提问逐步澄清，最终产出一份规范、可作为后续技术设计输入的需求文档。

这个技能的核心价值在于"填空"而不是"编造"：需求中模糊或缺失的部分，必须通过提问向用户确认，绝不能靠猜测直接补完生成一份看起来完整但实际是拍脑袋的文档。

## 何时使用本技能

用户给出一段原始需求描述（可能只有一两句话，也可能是一段较完整的想法），希望把它整理成规范的需求文档，供后续做技术设计或排期使用。使用本技能而不是直接手写文档，或者跳过澄清直接生成"看起来完整"的文档。

如果用户已经有一份成熟的需求文档，想要的是技术设计（架构、模块拆解、代码改动清单），那是 `tech-design-doc` 技能的职责，不要用本技能重复劳动。

## 不可违背的原则

1. **模糊点必须靠提问澄清，绝不能靠猜测填补。** 只要某个功能点、边界条件、验收标准存在歧义或缺失，就必须生成结构化问题让用户回答，不能为了"看起来完整"就自行假设一个答案写进文档。
2. **绝不基于猜测直接产出完整需求文档。** 除非用户明确说"不用再问了，按你的理解直接写"，否则必须先完成至少一轮澄清提问，且关键的功能边界、优先级、验收标准类问题必须得到用户确认。
3. **代码影响分析必须落到具体模块/文件。** 不能说"可能会影响相关模块"这种空话，要指出具体路径、具体函数/类，并说明为什么判断会受影响。
4. **调研结论必须标注来源和适用前提。** 网络调研得到的方案对比、行业实践，必须写明信息来源（链接/文档名），并说明这个结论在什么前提下适用——不能把调研内容当作无条件正确的结论直接写入文档。
5. **不做业务决策，只提供选项和分析。** 遇到需要业务判断的分岔点（比如两种功能路径都可行，选哪个取决于产品策略），把选项、优劣、推荐意见列出来，决策权交还给用户。
6. **不编写业务代码。** 本技能的产出物只是需求文档，即使为了验证技术可行性需要看代码，也只读不写业务代码。
7. **分阶段推进，不要一次性抛出大量内容。** 每次交互聚焦当前阶段的任务（收集信息 / 提问澄清 / 调研 / 出文档），不要把所有阶段的产出压缩到一条回复里。

## 标准工作流程

### 阶段一：信息收集

- 接收用户的原始需求描述，以及用户主动提供的代码文件/目录路径/参考资料。
- 如果用户没有提供任何代码上下文，主动询问：是否有相关项目代码、历史需求文档或参考资料可以结合分析？如果这是一个全新项目/全新方向，也要确认这一点，避免枉然去找不存在的代码。
- 不要在这一步做过多分析，先把输入信息收集完整。

### 阶段二：初步分析

- 阅读用户提供的代码（对于较大范围的代码，通过 Agent 工具委托子代理调研，报告需要包含：现有技术栈、模块划分、与本需求相关的业务逻辑、可能的改动点）。
- 输出一份简要的初步拆解，明确区分：
  - 已经明确的点（需求描述中已经说清楚的部分）
  - 待确认的模糊点（需要用户补充才能继续的部分）
- 这一步只是"摆现状"，不要在这里直接抛出全部问题清单——先让用户看到你对需求的理解是否准确，再进入提问阶段。

### 阶段三：需求细化提问

- 针对阶段二列出的模糊点和缺失项，整理成结构化问题清单。每个问题必须包含：
  - 问题本身（具体、有针对性，禁止"你还有什么其他要求吗"这类空泛问题）
  - 提问原因（为什么需要确认这个信息，它会影响文档的哪个部分或后续设计的哪个决策）
- 问题按维度归类，覆盖但不限于：功能边界、验收标准、技术约束、优先级、用户场景、异常/边界情况。
- 用户回复后，更新你对需求的理解，如果还有新的模糊点浮现（用户的回答引出了新问题），重复本阶段直到需求足够清晰、可以支撑写出验收标准和功能边界为止。
- 不要无限提问——一旦核心功能边界、优先级、验收标准都已明确，即可进入下一阶段，剩余的次要疑点可以放到文档末尾"待确认事项"里，不必卡住不推进。

### 阶段四：调研补充（视需要触发）

- 仅当需求涉及用户或项目代码中不熟悉的技术方案、行业规范、通用设计模式时才触发。如果需求很直白（比如"给列表加个筛选框"），不需要强行调研。
- 对涉及的技术点进行网络检索，整理：
  - 可选方案及其优缺点
  - 适用场景（这个方案在什么情况下合适，什么情况下不合适）
  - 参考来源（保留可核查的链接或文档出处）
- 调研内容是为了给用户在需求文档里提供技术选型参考，不是替用户做最终决定。

### 阶段五：文档输出

- 用户确认关键问题后，按下方固定模板生成完整需求文档。
- 文件命名固定为：`docs/request-<需求简称或唯一标识>-<YYYYMMDD>.md`，日期默认取今天。简称由需求核心内容提炼，如果用户已经指定了简称/标识，直接采用。
- 输出后简要说明文档结构，以及后续建议（例如：这份需求文档可以作为 `tech-design-doc` 技能的输入，用于生成技术设计文档）。
- 如果仍有未解决的次要问题，明确写入文档末尾"七、待确认事项"，不要藏在正文里。

## 固定输出模板

```markdown
# 需求文档：【需求全称】
> 文档编号：request-【简称】-【YYYYMMDD】
> 创建日期：【YYYY-MM-DD】
> 关联项目：【如有则填写】

## 一、需求背景与目标
1. 业务背景：需求产生的具体场景、要解决的核心问题
2. 预期目标：需求达成后的业务价值、技术价值
3. 关联范围：影响的业务模块、系统模块

## 二、核心功能需求
### 2.1 功能清单
按优先级（P0/P1/P2）拆分具体功能点，每个功能点描述清晰的用户场景与操作流程。
### 2.2 核心流程
描述核心业务/技术执行流程，补充关键节点说明。
### 2.3 边界定义
明确需求的「包含范围」与「不包含范围」（清晰界定做什么/不做什么）。

## 三、非功能需求
1. 性能要求：响应时间、并发量、资源占用等
2. 兼容性要求：适配环境、依赖版本限制等
3. 安全性要求：权限控制、数据安全等
4. 其他：可维护性、扩展性、可观测性等

## 四、技术约束与依赖
1. 现有技术栈约束
2. 依赖的第三方组件/服务
3. 代码改动影响范围
4. 潜在技术风险与应对建议

## 五、验收标准
对应每个功能点的可量化、可验证的验收条件。

## 六、调研补充信息（如有）
1. 技术方案调研结论
2. 行业最佳实践参考
3. 参考资料链接与来源说明

## 七、待确认事项
记录仍未明确、后续需同步的问题
```

## 实操要点

- **提问要分批、有优先级。** 先问会决定文档整体方向的问题（功能边界、核心场景），再问细节性的问题（异常处理、具体文案）。不要把十几个问题一次性甩给用户，容易让人无从下手——按维度分组，每组 3-5 个问题为宜。
- **代码调研同样委托子代理。** 涉及较多文件或不熟悉的模块时，用 Agent 工具（general-purpose 或 Explore）去读代码并structured汇报，主对话里只保留结论性的影响判断。
- **区分"确认型问题"和"选择型问题"。** 确认型问题（"这个功能只针对登录用户吗？"）通常可以直接问；选择型问题（"权限校验放在网关层还是服务层？"）应该先给出你的初步判断和理由，再请用户确认或调整，而不是把技术选型的判断责任完全推给用户。
- **不要在没有代码上下文时假装分析过代码。** 如果用户没提供代码，"技术约束与依赖"这一节就诚实写"未提供代码上下文，以下为基于需求描述的推测性约束，建议补充代码后复核"，不要编造具体文件路径。
- **调研来源要可核查。** 只引用能查到出处的信息，不要把记忆中的"大概是这样"当作调研结论呈现。
