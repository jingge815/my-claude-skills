# 单点性能问题修复工具

针对一个明确的性能问题（慢在哪、目标是什么），先测量、再定位、后修复，全程把每个数字关进 benchmark-checklist 的核验纪律里。核心价值是"证据链"：没有 trace 证据不许动手，没有七问核验不许报数。

## 不可违背的原则

1. **复现优先。** 必须先在真实负载上捕获 baseline trace，确认能复现"慢"，才允许提出修复假设；禁止只读源码就断言性能上限或瓶颈成因。
2. **每个数字过七问。** baseline 与修复后的每个数字，都按 `pstack/benchmark-checklist`（Read `~/.claude/skills/pstack/benchmark-checklist/SKILL.md` 并遵循）核验：瓶颈（limiter）是什么、两边是否都调优了、是否突破理论极限（做算术）、错误数是多少、能否复现（多次取中位数）、对端到端是否重要、计时区间内工作是否真的发生了。任何一问答不上来，该数字标为"不可信"或不报。
3. **性能咒语从最便宜试起，命中即停。** 依次为：不做（干掉没有消费方的工作）→ 不做第二次（缓存/记忆化）→ 少做（减量）→ 晚做（延迟/异步化）→ 背着做（避开关键路径时段）→ 并发做 → 便宜做（换更省的实现）。前面的咒语达到目标就停，不叠加后面的。
4. **跨函数边界的修复先走 architect。** 修复会改变接口、数据结构或模块职责时，先按 `pstack/architect`（Read `~/.claude/skills/pstack/architect/SKILL.md` 并遵循）比较两套形态再动手。
5. **一次一改一测。** 每个修复尝试独立验证（对照 baseline、跑回归门）后再试下一个；不堆叠未验证的改动；验证不通过完整回退该尝试。
6. **不做设计外的"顺便优化"。** 只修性能问题本身；看到的其他问题记录反馈，不顺手改。

## 标准工作流程

### 阶段一：复现与基线

- 明确性能问题的口径：什么操作、什么负载、多慢、目标多快（用户给了数字就用用户的）。
- 在真实负载上捕获 baseline trace（profiler、耗时统计、日志时间线），确认问题可复现。复现不了时先修复现环境，不进入定位。
- baseline 数字当场过七问，记录 limiter 初步判断与证据路径。

### 阶段二：定位

- 从 trace 出发把热点映射到源码（哪个函数、哪段循环、哪个 I/O），形成候选假设清单，按"能排除最多问题空间"的顺序逐个用运行证据排除，直到一个幸存。
- 假设必须点名具体机制（"X 阻塞了首屏，因为每个元素都同步调用 Y"），不接受"试试加个缓存"这类模糊假设。
- 负载生成器本身先饱和时，测到的是负载生成器——换负载方式再测。

### 阶段三：修复

- 按性能咒语排序候选方案，从最便宜的开始实施；跨函数边界的方案先走 architect。
- 实施可委托子代理（模型按 `dev-flow/config.toml` 的 worker.code 角色），主对话审 diff；在任务 worktree 内进行，不为性能修复另建 worktree。
- 修复后捕获 post-fix trace，与 baseline 同口径对比，跑相关回归门（命令来自项目 CLAUDE.md 的验证命令清单）。

### 阶段四：核验与报告

- post-fix 数字过七问；结论只有四选一：更快 / 更慢 / 无可测差异 / 不可信（说清缺哪问的证据）。
- 报告固定格式：baseline 数字、修复后数字、delta、limiter、trace 证据路径。一个数字不过七问不许出现在结论里。

## 实操要点

- **profiler 本身会拖慢被测程序**：定位用的 trace 运行不作为报数依据，报数用不带 profiler 的干净运行。
- **机器忙时先看负载**：`uptime`、`nproc`，有别的进程抢资源就交错运行两侧或换时间测，并在报告注明。
- **微基准必须配端到端**：占端到端 1% 的函数再快也只能快 1%，报告里写清楚占比。
- **拒绝"看起来更快"**：JIT 丢弃、惰性求值没触发、超时兜底等都会产生"没做工作却有了数字"的假象——确认计时区间内工作真的发生了（七问第 7 问）。
- **修完如果还要持续压指标**：转入 hill-climb 技能，把本次修复的测量脚本冻结为 harness 起点。
