# 技术设计文档生成器

把一份已确认的需求文档，转化为可直接落地开发的技术设计文档，且设计必须扎根于项目真实代码，而不是泛泛的模板套话。这份文档的定位是：**工程师拿着它就能直接开始写代码**——因此文档里的每一条结论都必须能追溯到需求文档的某一条，或者你亲自读过的某一段代码。

判断标准：把这份文档交给一个没参与过需求讨论的工程师，他能不能不提问就开始改代码？如果某处他还得回来问"这里具体怎么写"，那处设计就没做完。

## 何时使用本技能

用户提供（或指明路径）一份已确认的需求文档——通常在 `docs/request-<简称>-<YYYYMMDD>.md`——并希望针对当前项目产出对应的技术设计。遇到这类请求时使用本技能，而不是临时手写一份设计文档。

## 不可违背的原则

1. **需求文档是范围的唯一依据。** 绝不擅自扩大范围（加入需求未提及的功能），也绝不擅自缩小范围（遗漏任何 P0/P1 功能点）。如果需求文档存在歧义、矛盾，或缺少支撑某一节设计所需的信息，必须停下来明确指出，绝不擅自决策——统一记录到"十一、待确认事项"，其中会阻塞设计推进的问题要直接向用户提问确认后再继续。
2. **每一条设计结论都必须可追溯。** 涉及代码影响面的描述，必须对应到你实际打开过的真实文件路径/类/函数——绝不能编造"看起来合理"的路径。涉及需求覆盖的描述，必须能对应回输入需求文档里具体的需求编号或条目。
3. **写方案与结果，不写原则与分析过程。** 这是设计文档，不是设计札记。正文里只出现「已经定下来的做法」——具体的数据结构、函数签名、字段名、调用位置。不要写"原则一：真源唯一""空值必须有确定语义"这类抽象原则，它们不增加可执行性，只是把常识换个说法；也不要写你如何权衡、排除了哪些思路的心理过程。多方案对比如果确实需要保留，单独放一节或留在对话里，不要混进模块详细设计。语言上要求**准确、通俗易懂**：优先用中文，仅类名、函数名、字段名等英文专有名词保留英文；用短句直说，去掉一切铺垫、过渡与过度展开，只保留核心信息。
4. **章节先讲清问题和方案，功能点采用叙述式设计。** 文档以「功能点」为最小单位组织（一个功能点 = 一条可独立验收的行为改动），并遵守以下结构：
   - **需求背景与目标**：参照需求文档的原始需求表述，完整覆盖原始 prompt 的目标，不写成与需求脱节的泛化口号。
   - **现状基线**：开头先用一段话总体说明为解决什么问题，已有代码已经支持什么、尚不支持什么，再展示核心结构和调用链；不得一上来堆细节代码。
   - **总体设计概述**：先说明要解决的问题、当前不足和技术路线，再逐一列出关键子问题及对应方法；不能只写模块名或流程图。
   - **现有逻辑衔接**：先用文字说明为完成目标，需要在哪个既有流程的哪个阶段接入，以及数据和控制如何流动，再给调用示例。
   - **模块详细设计**：开头用一段话说明涉及哪些模块及模块关系。每个小标题只写功能点名称，不附需求编号、代码位置、改动类型等元信息；随后用 1～2 段文字说明要解决的问题、现有不足、需要新增/修改的模块或功能、解决思路、对应需求及真实代码位置。行为改动须给出「原有/目标」关键代码对比，代码不能代替文字叙述，也不要使用“功能点/原因/解决思路”等标签堆砌内容。
   - **改动汇总**：先用一段话说明涉及几个代码仓库、分别有哪些功能模块修改，再列文件级清单。
   - **验证与测试方案**：开头先用一段话总体说明单元、集成、兼容、端到端等验证层次，再列具体用例。
   叙述应简洁、可直接实施，代码位置与需求映射放在正文中，不堆进小标题。
5. **优先复用现有技术栈。** 尽量沿用项目当前的库、框架与既有模式。如果确实需要引入新依赖或新模式，必须给出明确理由（说明现有方案为何不可行）并注明引入成本。
6. **验证方案不能笼统。** 每一个测试用例都要有具体的操作步骤和可核对的预期结果，"测试xxx功能正常"这类描述是不合格的。优先给出可直接粘贴运行的断言代码。
7. **文件命名固定为：** `docs/design-<需求简称或唯一标识>-<YYYYMMDD>.md`。`<需求简称或唯一标识>` 应从输入需求文档自身的文件名或其标注的需求编号中提取——如果源文档已经有简称/标识，不要另起一个。
8. **设计文档覆盖需求文档的所有目标**
9. **设计核心目标要参照完整贴合原始的prompt需求，甚至可以直接照搬或者进一步扩展；**
10. **总体设计上要从抽象从原理上说明当前采用的关键核心技术。**

## 标准工作流程

严格按以下阶段顺序执行，不要跳过分析阶段直接开始写文档——这份设计的价值恰恰来自于对真实代码的深入了解，而这需要先把代码真正读一遍。

### 阶段一：输入接收与对齐

- 定位并完整阅读需求文档（用户直接给出路径，或者如果只说了功能名称，就在 `docs/request-*.md` 中搜索匹配）。
- 提取所有功能点，并按源文档标注的优先级打上 P0/P1/P2 标签（如果源文档没有标注优先级，向用户确认应如何处理，不要自行猜测）。
- 提取所有验收标准与约束条件（性能、兼容性、安全性、时间节点等）。
- **需求文档若来自本技能的上游流程，它可能夹带未经验证的技术断言。** 设计阶段要以代码为准复核关键前提（尤其是"某组件负责 X""这条信息流经 Y"这类），发现与需求描述不符时按原则 1 处理。
- 如果用户没有说明需要分析哪些代码目录/模块，先向用户确认涉及的代码范围，再开始大范围扫描——对于范围明确的小功能，不要默认扫描整个仓库；对于跨模块的改动，也不要把范围划得过窄。
- 如果需求文档本身不完整或存在自相矛盾、且这种问题会阻塞设计推进（而不是可以先标注、继续往下走的小歧义），此时应停下来向用户确认，而不是自行猜测后继续。

### 阶段二：代码基线与影响面分析

- 阅读约定范围内的真实代码：现有架构分层、模块职责划分、调用链路、数据结构，以及新需求将要触碰或必须对接的具体接口/函数。
- 对于规模不小的范围（涉及较多文件，或你不熟悉的代码区域），应通过 Agent 工具委托子代理（或 fork）去完成这部分阅读，而不是在主对话里做大范围手动阅读——要求子代理具体汇报：文件路径、当前职责、调用点，以及任何看起来会与新需求产生冲突的地方。范围较小且熟悉的代码可以直接阅读。委托回来的结论中若有支撑关键设计决策的部分，自己再核实一遍。
- 建立"需求—代码"的影响面映射：哪些现有模块需要改动，哪些是全新模块，哪些模块仅因为调用了被改动的代码而需要做回归验证。
- 记录需要遵循的现有约定：命名规范、错误处理风格、测试框架、分层规则——设计必须贴合这些约定，不能另起一套风格。**错误信息用中文还是英文、异常类型用哪个、dataclass 是否 frozen——这些都要照抄现有代码的做法，而不是照搬你熟悉的写法。**
- 记录现有代码里的"隐含假设"——某处按某个前提算出结果，而这个前提不写在任何参数、字段或注释里。（举一个直觉上不相干的例子：一段代码按元素个数乘元素宽度得出占用空间，等价于假定数据在内存里连续紧密排列；这个前提一旦不成立结果就是错的，但代码里看不出来。）这类约定俗成是本轮设计最需要显式化的对象，也最容易漏掉。

### 阶段三：方案设计

- 先给出总体设计，逐模块细化。总体设计不是引言，它本身要承载实质技术方案内容。
- 每个功能点不仅要描述问题,当前现状,还要给出具体的解决方案。
- 如果某个技术决策确实存在不确定性（需要用户或技术负责人拍板），不要自行悄悄决定——可以给出你的推荐意见，但同时把它列入"十一、待确认事项"。

### 阶段四：输出设计文档

- 完整填写下方固定模板的每一节。所有章节都必须有内容——如果某一节确实不适用（例如没有性能要求），要明确写"无"并说明原因，而不是直接删掉这一节。
- 5.1 的文件级改动清单必须精确到可以直接拆解为开发任务的程度：真实路径、真实改动类型、具体的改动描述、明确的下游影响范围，以及继承自对应需求的优先级。
2- 将文件写入 `docs/design-<简称>-<YYYYMMDD>.md`，日期默认取今天，除非用户另有指定, 整体篇幅不能超25000字!!!
- **输出前自检**：逐章检查开头是否有要求的总体叙述；逐个功能点检查小标题是否只含名称，正文是否写清问题、现状不足、方案、需求映射和代码位置，行为改动是否有「原有/目标」代码对比。任一条不满足，就重写该功能点。

### 阶段五：澄清与迭代

- 文档初稿完成后，把所有未解决的问题明确列在"十一、待确认事项"中——不要只在正文里零散提一下就算了。
- 当用户给出决策或修改意见后，在原文件上直接更新（不要新建第二份文件），并同步检查该决策会影响到的其他章节（范围变化通常会牵动总体设计、模块详细设计、改动汇总与验证方案）。**改动章节编号后，全文的 `§x.y` 交叉引用要一起改**，改完做一次悬空引用检查。
- 设计过程中若发现自己的先前判断有误，在文档里单开一节记录「本设计自身的修正记录」：原结论 → 错在哪 → 修正后的结论。这比悄悄改掉更有价值，因为下游可能已经看过旧版本。

### 阶段六：迭代与校对
- 设计文档完成后，要再根据需求文档，进行一次整体的对照检查，确保所有需求点都被覆盖，且设计方案与需求文档保持一致。

## 实操要点

- **必要时引用具体行号。** 引用现有函数或接口时，使用 `path/to/file.py:123` 这样的格式，方便阅读者直接跳转过去。
- **不要为了凑字数而堆砌内容。** 输出尽可能可读且简洁,特别注意篇幅,如果某一节的真实答案就是很简短（例如"无破坏性变更，无需特殊回滚步骤"），就写得简短。这里衡量质量的标准是可追溯性和可执行性，不是篇幅长短。
- **贴合项目现有代码风格，而不是个人偏好。** 如果项目已经有明确的约定（CLAUDE.md、lint 配置、现有模块的写法），设计必须遵循这些约定，即便你认为另一种写法在技术上更优雅。
- **重构类需求的关键判据是「产出完全一致」。** 如果本轮是"把散落各处的东西收拢到一处"，而不是"增加新能力"，那么最重要的验收条件就是改动前后产出完全一致——能逐字节比对的就逐字节比对（导出文件、生成的配置、接口响应），不能逐字节比对的就给出等价性断言。把这条写进验证方案，并在设计里说明每个改动点凭什么不改变行为。
- **给已有结构加字段时，默认值要选成"等价于改动前的行为"。** 并把这个对应关系写进字段注释。这样既有代码路径不改也保持一致，也让"哪些是新能力、哪些只是把隐含假设显式化"一目了然。
- **写完一个章节后做覆盖性回查。** 逐个需求编号问一遍：这条在文档哪一节、结论是什么？找不到落点的说明漏了；只有一个表格没有代码的，说明还没设计完。
- **多轮对话兼顾新内容和原始目标** 紧扣原始需求，兼顾新需求和原始需求，不要偏离核心目标。
