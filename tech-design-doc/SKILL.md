# 技术设计文档生成器

把一份已确认的需求文档，转化为可直接落地开发的技术设计文档，且设计必须扎根于项目真实代码，而不是泛泛的模板套话。这份文档的定位是：工程师拿到它就能直接开始写代码——因此文档里的每一条结论都必须能追溯到需求文档的某一条，或者你亲自读过的某一段代码。

## 何时使用本技能

用户提供（或指明路径）一份已确认的需求文档——通常在 `docs/request-<简称>-<YYYYMMDD>.md`——并希望针对当前项目产出对应的技术设计。遇到这类请求时使用本技能，而不是临时手写一份设计文档。

## 不可违背的原则

1. **需求文档是范围的唯一依据。** 绝不擅自扩大范围（加入需求未提及的功能），也绝不擅自缩小范围（遗漏任何 P0/P1 功能点）。如果需求文档存在歧义、矛盾，或缺少支撑某一节设计所需的信息，必须停下来明确指出，绝不擅自决策——统一记录到"十、待确认事项"，其中会阻塞设计推进的问题要直接向用户提问确认后再继续。
2. **每一条设计结论都必须可追溯。** 涉及代码影响面的描述，必须对应到你实际打开过的真实文件路径/类/函数——绝不能编造"看起来合理"的路径。涉及需求覆盖的描述，必须能对应回输入需求文档里具体的需求编号或条目。
3. **优先复用现有技术栈。** 尽量沿用项目当前的库、框架与既有模式。如果确实需要引入新依赖或新模式，必须给出明确理由（说明现有方案为何不可行）并注明引入成本。
4. **验证方案不能笼统。** 每一个测试用例都要有具体的操作步骤和可核对的预期结果，"测试xxx功能正常"这类描述是不合格的。
5. **文件命名固定为：** `docs/design-<需求简称或唯一标识>-<YYYYMMDD>.md`。`<需求简称或唯一标识>` 应从输入需求文档自身的文件名或其标注的需求编号中提取——如果源文档已经有简称/标识，不要另起一个。

## 标准工作流程

严格按以下阶段顺序执行，不要跳过分析阶段直接开始写文档——这份设计的价值恰恰来自于对真实代码的深入了解，而这需要先把代码真正读一遍。

### 阶段一：输入接收与对齐

- 定位并完整阅读需求文档（用户直接给出路径，或者如果只说了功能名称，就在 `docs/request-*.md` 中搜索匹配）。
- 提取所有功能点，并按源文档标注的优先级打上 P0/P1/P2 标签（如果源文档没有标注优先级，向用户确认应如何处理，不要自行猜测）。
- 提取所有验收标准与约束条件（性能、兼容性、安全性、时间节点等）。
- 如果用户没有说明需要分析哪些代码目录/模块，先向用户确认涉及的代码范围，再开始大范围扫描——对于范围明确的小功能，不要默认扫描整个仓库；对于跨模块的改动，也不要把范围划得过窄。
- 如果需求文档本身不完整或存在自相矛盾、且这种问题会阻塞设计推进（而不是可以先标注、继续往下走的小歧义），此时应停下来向用户确认，而不是自行猜测后继续。

### 阶段二：代码基线与影响面分析

- 阅读约定范围内的真实代码：现有架构分层、模块职责划分、调用链路、数据结构，以及新需求将要触碰或必须对接的具体接口/函数。
- 对于规模不小的范围（涉及较多文件，或你不熟悉的代码区域），应通过 Agent 工具委托子代理（或 fork）去完成这部分阅读，而不是在主对话里做大范围手动阅读——要求子代理具体汇报：文件路径、当前职责、调用点，以及任何看起来会与新需求产生冲突的地方。范围较小且熟悉的代码可以直接阅读。
- 建立"需求—代码"的影响面映射：哪些现有模块需要改动，哪些是全新模块，哪些模块仅因为调用了被改动的代码而需要做回归验证。
- 记录需要遵循的现有约定：命名规范、错误处理风格、测试框架、分层规则——设计必须贴合这些约定，不能另起一套风格。

### 阶段三：方案设计

- 先给出总体方案：技术选型、核心流程、如何嵌入现有架构的分层结构。
- 如果确实存在多种可行方案（而非只有一条路可走），给出 2-3 个具体方案，并做真实的优劣对比（开发成本、风险、性能、可维护性），最终给出推荐建议并说明理由——绝不能只给结论不给依据。
- 把每个受影响模块的设计做到足够细，使模板第三节能够填入真实的实现逻辑，而不是把需求原文再复述一遍。
- 如果某个技术决策确实存在不确定性（需要用户或技术负责人拍板），不要自行悄悄决定——可以给出你的推荐意见，但同时把它列入"待确认事项"。

### 阶段四：输出设计文档

- 完整填写下方固定模板的每一节。所有章节都必须有内容——如果某一节确实不适用（例如没有性能要求），要明确写"无"并说明原因，而不是直接删掉这一节。
- 第四节的文件级改动清单必须精确到可以直接拆解为开发任务的程度：真实路径、真实改动类型、具体的改动描述、明确的下游影响范围，以及继承自对应需求的优先级。
- 将文件写入 `docs/design-<简称>-<YYYYMMDD>.md`，日期默认取今天，除非用户另有指定。

### 阶段五：澄清与迭代

- 文档初稿完成后，把所有未解决的问题明确列在"十、待确认事项"中——不要只在正文里零散提一下就算了。
- 当用户给出决策或修改意见后，在原文件上直接更新（不要新建第二份文件），并同步检查该决策会影响到的其他章节（范围变化通常会牵动第三、四、六、八节）。

## 实操要点

- **把代码阅读委托出去。** 只要涉及不止一两个文件，就用 Agent 工具（general-purpose 或 Explore）去调研受影响的区域，并要求它把结果结构化汇报回来——文件路径、职责、调用点——而不是在主对话里逐个文件阅读，占满上下文。把这些调研结果作为阶段三设计工作的输入。
- **必要时引用具体行号。** 引用现有函数或接口时，使用 `path/to/file.py:123` 这样的格式，方便阅读者直接跳转过去。
- **不要为了凑字数而堆砌内容。** 如果某一节的真实答案就是很简短（例如"无破坏性变更，无需特殊回滚步骤"），就写得简短。这里衡量质量的标准是可追溯性和可执行性，不是篇幅长短。
- **贴合项目现有代码风格，而不是个人偏好。** 如果项目已经有明确的约定（CLAUDE.md、lint 配置、现有模块的写法），设计必须遵循这些约定，即便你认为另一种写法在技术上更优雅。
- **多个结构相似的模块要分别展开。** 比如三个类似的 handler，如果它们的改动内容有实质差异，就应该分别写成 3.1、3.2、3.3，而不是笼统合并成一段模糊描述；但也不要为了减少文档中的重复，凑出一个需求里并不存在的抽象层。
