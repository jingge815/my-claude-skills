# 项目申请书转 10 分钟答辩 PPT

把一份已经写好的项目申请书，转成一套可以照着讲的答辩材料：**一份按参考模板排版的可编辑 pptx**，
加上**一份逐页对应、总字数卡在 10 分钟以内的答辩旁白稿**。

这个技能只做"提炼与搬运"，不做"创作"。幻灯片上的每一句话都必须能在申请书原文里找到出处；
旁白是把申请书的内容换成能开口讲的话，不是另写一套说辞。凡是申请书里没有的研究内容、技术指标、
成果数量，一律不写——宁可少一页，也不许填一个编出来的数字。

但"只搬不写"不等于照抄。同一段原文，读懂了、概括过的，和直接贴上去的，是两份完全不同的
PPT。所以这个技能真正考验的是三件事：**读懂申请书的逻辑**、**把长文压成短句**、
**把关系画成图**。

## 何时使用本技能

用户已经有一份成稿的项目申请书（或项目建议书、课题申报书），现在要据此做答辩汇报。典型输入是
申请书文件，加上可选的申请人姓名、答辩日期、单位技术积累补充材料。

不适用的情况，改走对应技能：

- 用户要**写**申请书、重构研究性表述 → `grant-writing`。
- 用户只要从某份 PPT/Word 里抽出排版做成通用格式技能 → `format-replica-skill-gen`。
- 用户要需求文档、技术设计、代码实现或代码评审 → `requirement-doc`、`tech-design-doc`、
  `tdd-implement`、`code-review-doc`。

本技能只新增、只维护 `proposalword2ppt/` 这一个技能目录。

## 不可违背的原则

做这套 PPT，成色取决于三件事：**真读懂申请书**、**把文字高度概括**、**把图画好**。
下面每一条都是这三件事的展开。

1. **先读透，再动笔。** 动 checklist 之前，先通读申请书的「需求分析 → 研究现状 →
   研究目标 → 研究内容 → 技术路线 → 指标 → 成果」这条主线，弄清这个项目到底在解决
   什么问题、用什么思路解、分成哪几块、每块的关键动作是什么。读不透就只能抄句子，
   而抄句子做不出好 PPT。读完后先落一张「页面 → 章节 → 该页要点」的映射表再开工。
2. **原文是唯一事实来源。** 页面上的研究内容、技术路线、指标数值、成果数量、经费科目、进度时间，
   全部逐条对应申请书原文。禁止补写申请书里没有的内容，禁止把"预期指标"写成"已达到"，禁止
   为了凑满版面而扩写。
3. **页面结构固定，不增不减。** 页序、页标题、每页承担什么内容，全部按下面的「页面规格」执行。
   研究内容多于两项时，只按「研究内容 N + 研究技术路线 N」成对顺延，不新增其他页型。
4. **严格照模板，不改版式。** 字体族、配色、位置、背景、标识全部来自
   `assets/template.pptx`，用 `scripts/build_ppt.py` 填充生成。不要另起炉灶手工排版，
   不要"顺手优化"模板样式。**字号不固定，但分档**：正文要点 12–18 磅按框自适应，
   封面标题固定 44 磅（微软雅黑居中）、封面信息 20 / 18 磅、图内文字 16–18 磅，
   总结句 12–16 磅。族名与各档实测值见 `references/template-spec.md` 第四节。
5. **高度概括，不许堆字。** 这是本技能的第二项硬功夫。一页原文往往几百字，上 PPT 的
   要压到 3–5 条、每条一句话，写成「标签：说明」；压不动就先想清楚这句到底在说什么，
   再换更短的说法，而不是截断原句。底部的总结句要落在一个判断上，不是继续罗列。
   条数上限 6 条（一般页 3–5 条）。字多了先靠降字号消化，12 磅仍溢出就减要点。
6. **图表必须画出来，而且必须是能看清、能编辑的图，不许交占位、不许交文字表格。**
   模板图表槽只是一块「图/表」色块。自己画的图由 `scripts/shapes.py` 生成
   **PPT 原生形状**（文本框、圆角矩形、箭头、饼图扇区），在 PowerPoint 里能点选、
   能改字、能挪框、能换色——**不许塞一张位图了事**。只有申请书原图（`type: image`）
   才是位图。图内文字 16–18 磅，字号由脚本按磅换算，不许靠压字号塞内容。
   禁止用 `table` / `cards` 把申请书段落改写成格子里的句子交差。
   数字必须来自申请书，没有量化数据时改画结构图，禁止用假数据凑图。
7. **先读懂那一节，再决定画什么。** 需求分析、研究现状不是把要点分两栏摆上去，
   而要读出因果关系（痛点 → 缺口 → 本课题回应），用 `logic` 画成带箭头的逻辑链。
   技术路线要读「研究思路方法与技术路线」，抽出步骤和每步子动作，用带 `children`
   的 `flow` 画成分层流程。研究内容要读出部件划分，用 `framework` 画成分层结构。
8. **图要美观、简洁，并且不许压字。** 一张图只讲一件事，层次清楚、对齐整齐、留白均匀；
   同页的框大小一致、色彩取自模板主题色，不要为了填满而堆节点。**简洁不等于简陋**：
   图里要能看出结构（谁包含谁、谁先谁后、谁导致谁），节点之间用箭头或层级把关系画出来。
   **排版铁律：任何"标签带 + 内容框"的图，都要给标签留独立的行高**——层名、时间轴刻度、
   表头这类文字必须先算出自己占多高，内容框从它下面开始；内容框一律**不填色**（透明），
   这样即使挨得近也不会把文字盖住。分层框架的层名被白框遮住、甘特图的「1–6 月」被
   柱子压住，都是同一个原因。怎么选、怎么画、各种图的密度上限，见 `references/figure-spec.md`。
9. **图优先来自申请书，没有就仔细画。** 申请书里该章节有能对上的图，**先把它复制进
   PPT 用**（`extract_doc.py` 抽到 `_media/`，按 `image` 嵌入），再酌情处理：图注、
   水印、多余留白可以裁掉；投影下字太小或只是表格截图，就按它的结构重画一张，
   宁可重画也不要放一张看不清的图。申请书**没有图**时，自己要画，而且要**仔细画**：
   读透该节，把结构、步骤、层次都画出来，节点该有几个就画几个，不要交一张只有三个
   空框的简图；图内文字按 16–18 磅，投影后后排能看清。
10. **第 2 页是核心考核项。** 技术积累页决定评审对"这个团队能不能干成"的第一判断，内容密度
    必须高于其他页。**固定写四条**：发表论文、项目经验、合作厂商、编译优化——每条都要带数量
    或名录（几篇什么级别 / 哪些项目 / 哪些厂商 / 覆盖多少优化点、提升多少），
    论文按团队口径统计。底部总结句落在"积累深厚、论文含金量高、项目经验丰富"这个判断上。
    逐条句式见 `references/content-spec.md`。
11. **缺失的核心章节必须问，不许编。** 申请书中找不到「编译领域技术积累 / 研究基础」这类核心
    章节时，停下来向用户要补充材料，不得用申请书里其他内容拼凑，更不得编造论文与项目。
12. **旁白总量卡死在 1800–2000 字。** 少于 1800 字撑不满 10 分钟，多于 2000 字讲不完。
    按 `references/narration-spec.md` 的逐页字数基准分配，写完逐页统计、核对总量。
13. **旁白的数字与申请书一致。** 旁白可以换说法、可以口语化，但不许改动任何数字、比例、
    时间点与结论强度。

## 输入与缺失处理

| 输入 | 要求 |
|---|---|
| 项目申请书全文 | **必选**。Word（.docx）用 `scripts/extract_doc.py` 抽取；PDF 用 Read 工具直接读 |
| 申请人姓名、答辩日期 | 选填，用于封面右下角；未提供就向用户要，或先留占位并在生成说明里标注 |
| 单位技术积累补充材料 | 选填，仅在申请书缺该章节时使用 |

缺失处理规则：

- 缺**核心章节**（编译领域技术积累 / 研究基础）：必须主动询问用户补充，不得自行编造，也不得
  用申请书其他章节拼凑。可以先完成其余页面的内容提炼，把这一页挂起等材料。
- 缺**非核心章节**（如经费预算、成果考核）：先基于已有内容生成，不要因此停下；在「生成说明」
  里逐条列出缺了哪页的哪些信息、建议用户补什么。
- 申请书写了但要点太散（一大段里找不到可提炼的点）：允许概括，但概括后的事实边界不得超出
  原文；概括不出来就说明该页信息不足，请用户指定口径。

## 标准工作流程

四个阶段依次推进，不要跳阶段，也不要把四件事塞进一次回复就宣布完成。

### 阶段 1：文档解析与章节映射

1. `.docx` 走脚本，PDF 走 Read：

   ```bash
   python3 scripts/extract_doc.py --input 申请书.docx --out 申请书.md
   python3 scripts/extract_doc.py --input 申请书.docx --headings-only
   ```

   `--headings-only` 先看章节骨架，再做映射，比通读全文快。PDF 用 Read 工具按页读，
   篇幅大时分段读，不要只看开头。

2. 按下面的对应关系把申请书章节映射到 PPT 页，形成一张映射表；映射不上或一个章节被拆到
   多页时，在「生成说明」里写清楚。

   | PPT 页 | 对应申请书章节 | 提取优先级 |
   |---|---|---|
   | 第 1 页 封面 | 项目全称、申请人信息 | 最高 |
   | 第 2 页 积累 | 研究基础与工作积累、已发表论文、承担项目、获奖成果 | 最高（核心考核项） |
   | 第 3 页 需求分析 | 研究背景与意义、需求分析、问题提出 | 高 |
   | 第 4 页 研究现状 | 国内外研究现状、现有方法不足 | 高 |
   | 第 5 页 研究概述 | 研究目标、总体研究思路、核心方案 | 高 |
   | 第 6–9 页 内容/路线 | 具体研究内容及其对应技术路线 | 高 |
   | 第 10 页 技术指标 | 主要技术指标、性能参数 | 中 |
   | 第 11 页 成果考核 | 预期成果、考核指标、验收方式 | 中 |
   | 第 12 页 周期进度 | 研究周期、进度安排、阶段计划 | 中 |
   | 第 13 页 经费预算 | 经费预算、支出明细 | 中 |
   | 第 14 页 结束语 | ——（固定页） | —— |

3. 数清楚申请书里到底有几项研究内容。**一对「研究内容 N + 研究技术路线 N」占两页**，
   2 项 = 标准 14 页方案，3 项 = 16 页，依此类推。这一条决定了最终的页数。

4. 阶段产物是一张「PPT 页 → 申请书章节 → 该页拟用要点」的映射表，落盘给用户确认后再进入
   阶段 2。映射表里如果出现"申请书中未找到对应内容"的行，就是需要向用户确认的地方。

### 阶段 2：逐页内容生成

**先读 `references/content-spec.md`**——那是逐页内容规范：每页写什么、几个栏目、什么句式、
总结句套哪个模板，都在里面。读完再动笔，不要凭印象写。

按页规格逐页提炼。**所有正文来自申请书，只提炼不照抄**；每页要点控制在 3–5 条（第 2 页固定
4 条），写成「标签：说明」；底部总结句按该页的固定句式写，不是随便一句判断。字号由脚本按框适配，
不必按固定 20 字去砍句子，但 12 磅仍溢出时必须减要点。

概括的要领：先想清楚"这条到底在说什么"，再换短说法，而不是把原句截断。一段三百字的
研究内容，上 PPT 只留它的目标、关键技术、出口三件事；

写 `content.json` 之前先读 `references/figure-spec.md`，给**每一页**（封面、结束语除外）
写一个 `figure` 对象。选型顺序：

1. **申请书该章节有能对上的图 → 复制过来用**，`{ "type": "image", "path": "…_media/imageN.png" }`，
   并在生成说明里注明来自申请书哪一张。复制过来后酌情裁掉图注、边框、水印与大片留白。
2. **原图看不清或只是表格截图 → 按它的结构重画**，别原样嵌一张投影下读不清的图。
3. **没有原图 → 自己画，而且要仔细画**：有表或量化数据用 `table` / `bar` / `pie` / `gantt`；
   只有结构用 `framework` / `flow` / `logic` / `compare` / `cards`。节点该有几个就画几个，
   不要交一张三个空框的简图。
4. 绝不把 `figure` 写成一句「配图说明」交差。
5. 需求、现状两页按申请书该节画 `logic` 逻辑链（痛点 → 缺口 → 回应 / 路线 → 不足 → 方向），
   不要把要点分成两栏摆上去。技术路线页必须 `flow` 且步骤带 `children`，
   同时右侧写 3–5 条要点——不许只有图、也不许只有三个空框。
6. 每一张图只取**本页对应章节**的事实。研究内容 N / 技术路线 N 不得搬其他
   章节的架构（典型错误：研究内容页出现申请书里另一处的「存算一体硬件模拟平台架构」）。
7. 图要美观、简洁，但简洁不等于简陋：层次清楚、框对齐、留白均匀、颜色只用模板主题色，
   并且一眼看得出结构——谁包含谁、谁先谁后、谁导致谁。

| 页 | kind | 标题 | 布局 | 内容要点 |
|---|---|---|---|---|
| 1 | `cover` | 项目申请书完整全称 | 居中，无配图 | 标题 + 右下角三行：`报告人：xxx` / `中国科学院软件研究所` / `xxxx年xx月xx日`；副标题选填。单位行可用 `org` 覆盖 |
| 2 | `accumulation` | 中国科学院软件研究所：编译领域积累 | 左大图、右文字、底部通栏总结 | 固定四栏：**发表论文 / 项目经验 / 合作厂商 / 编译优化**，每栏都带数量或名录。论文按团队口径统计。句式见 `references/content-spec.md` |
| 3 | `text-left` | 需求分析 | 左文右图 | 研究问题背景、行业痛点、研究必要性与应用价值。图按 `logic` 画成因果链 |
| 4 | `text-left` | 研究现状 | 左文右图 | **每条路线都要写全「原理 + 不足」**：先说这条路线怎么做（基于什么、把什么映射成什么），紧接着说它缺什么。见下方专门说明 |
| 5 | `figure-left` | 研究概述 | 左图右文 | 总体思路、核心方案、拟解决的关键问题、与现有研究的差异。**图优先用申请书的原框架图**，没有就自己画 |
| 6… | `figure-left` | 研究内容 N | 左图右文 | 第 N 项研究内容的核心目标、关键技术点、解决的具体问题。结构图可用申请书原图（如「架构框图」），没有就按该节画 `framework`。底部总结句见下方模板 |
| 7… | `figure-left` | 研究技术路线 N | 左图右文 | 左：申请书有路线图就用原图，没有就按该节画分层流程图（3–5 步，每步有子步骤）；右：实现路径、技术步骤、关键方法。两边都要有，不能只有图。底部总结句见下方模板 |
| — | `figure-left` | 主要技术指标 | 左图右文 | 核心量化指标、性能参数、与现有技术的对比优势 |
| — | `figure-left` | 研究成果及考核方式 | 左图右文 | 预期产出（论文、专利、软著、原型系统）与验收考核标准 |
| — | `figure-left` | 研究周期与进度安排 | 左图右文 | 总周期、分阶段任务、关键节点里程碑 |
| — | `figure-left` | 经费预算 | 左图右文 | 总预算、主要支出科目、预算分配逻辑 |
| 末页 | `closing` | 结束语 | 居中，模板自带 ISCAS 标识 | 收尾判断落在**软件所的优势**上（编译方向长期积累、质量保证与国产化保障能力、研制能力）+ 「感谢各位评审专家！」。默认文案见下，可按项目微调，但不能改成空泛的感谢 |

「研究内容 N」与「研究技术路线 N」严格成对出现、相邻排列，标题按中文数字顺延
（研究内容一 / 技术路线一 / 研究内容二 / 技术路线二……）。

**每页写什么、几个栏目、什么句式，全部照 `references/content-spec.md`。**
上面这张表只定结构和位置，具体措辞以那份规范为准——两处冲突时以 content-spec 为准。
最容易写走样的是这四处，动手前先翻过去看一眼：

- 第 2 页固定四栏：发表论文 / 项目经验 / 合作厂商 / 编译优化，每条都要带数量或名录。
- 第 4 页每条路线写全「原理 + 不足」，不是只说一句"存在不足"。
- 研究内容页总结句：「针对〈问题〉，已有方法〈不足〉，研究〈技术〉」。
- 技术路线页总结句：「提出/设计〈方法〉，相比于原有〈方法〉，优势在于〈新在哪〉」。

### 阶段 3：答辩旁白生成

按 `references/narration-spec.md` 执行，要点复述如下：

- 总字数 1800–2000 字，按每分钟 200 字折算约 9–10 分钟。
- 先分配字数再动笔：重点页（第 2 页、第 5 页）各不少于 200 字，封面与结束语各不超过 90 字，
  其余按基准表分。
- 说人话，不念 PPT：幻灯片上有要点，旁白补"为什么"和"所以呢"；页间用语承接上，不要每页都用
  同一个开场句式。
- 每页标注本页字数，末尾给出总字数与折算时长。
- 旁白里的数字逐个与申请书核对。

### 阶段 4：落盘生成与质量校验

1. 把阶段 2、3 的内容写成 `content.json`（契约见 `references/template-spec.md` 第六节），
   然后生成：

   ```bash
   python3 scripts/build_ppt.py --content content.json \
           --out 答辩PPT-<项目简称>-<YYYYMMDD>.pptx \
           --narration-out 旁白稿-<项目简称>-<YYYYMMDD>.md
   ```

   脚本会打印逐页报告（要点条数/字数、实际字号、图是原生形状还是原图、总结字数、
   旁白字数、折算时长）并给出 `[校验]` 提示。拿到 `[校验]` 不要直接交付，
   先按提示改 `content.json` 再重新生成。

   自己画的图由 `shapes.py` 生成原生形状，**不需要 Pillow**；只有嵌申请书原图和
   出预览图时才用到它，缺了就 `pip install pillow`。

2. 按清单自查，逐条确认：

   - [ ] pptx 页数 = 1（封面）+ 1（积累）+ 3（需求/现状/概述）+ 2N（内容/路线）+ 4（指标/成果/周期/经费）+ 1（结束语）
   - [ ] 每页要点 ≤6 条；正文字号 ≥12 磅；封面三行（报告人 / 单位 / 日期）20 磅起；脚本报告无未消化的溢出
   - [ ] 除封面、结束语外，每一页图表槽都是图或表，没有「图/表」三字占位
   - [ ] 正文框与图表槽上下沿对齐，文字没有压到图上
   - [ ] 申请书里有能对上的原图的页，已把原图复制进来并酌情裁切，来源写进生成说明
   - [ ] 自己画的图在报告里显示为「形状图 N 个（可编辑）」，在 PowerPoint 里点得开、改得动
   - [ ] 需求分析、研究现状是带箭头的逻辑链（`logic`），不是两栏要点或表格
   - [ ] 自己重画的图是流程 / 逻辑链 / 分层框架 / 左右对比，图内文字 16–18 磅肉眼能读；技术路线页图文都有
   - [ ] 自己画的图够丰富（结构、步骤、层次都在），不是一张三个空框的简图
   - [ ] 图美观简洁：框对齐、留白均匀、颜色只用主题色，一眼看得出关系
   - [ ] 层名 / 轴标签 / 表头都有独立行高，内容框不填色，没有被白框或柱子压住
   - [ ] 第 2 页按「发表论文 / 项目经验 / 合作厂商 / 编译优化」四条写，论文按团队口径统计，
         项目与优化点都带数量，不是光列名字
   - [ ] 第 4 页每条路线都写了「原理 + 不足」，不是只有一句"存在不足"
   - [ ] 研究内容 / 技术路线的总结句用了各自的固定句式，且一行放得下（未压到 14 磅以下）
   - [ ] 封面标题是微软雅黑 44 磅居中
   - [ ] 图表配色只有模板主题色；饼图/柱状图/表格里的数字能在申请书里找到
   - [ ] 每张图只对应本页章节，没有把其他章节的架构图挪过来
   - [ ] 结束语落在软件所的优势判断上，不是一句空泛的感谢
   - [ ] 旁白总字数在 1800–2000 之间，重点页 ≥200 字，封面/结束语 ≤90 字
   - [ ] 抽取到的每一条内容都能在申请书原文里指出出处，没有编造项
   - [ ] 缺章节、信息不足、口径存疑的地方，全部写进了「生成说明」
   - [ ] 模板样式未被改动（字体族、配色、背景、页码、ISCAS 标识齐全）
   - [ ] 旁白已写入备注页（PowerPoint 备注区可见），且与旁白稿一致

3. **生成后一定看图。** 首选 `shapes.to_preview_png()`——把每页的图按同一套几何
   画成 PNG，直接看有没有压字、出框、字太小：

   ```python
   import shapes
   shapes.to_preview_png(shapes.render_shapes(page["figure"]), "预览-第N页.png")
   ```

   有 LibreOffice 时也可以 `soffice --headless --convert-to pdf` 看整体版式。
   两者都不可用时，才退而以脚本报告的校验为准，并在交付说明里注明"未做视觉复核"。

## 输出格式

一次交付三样东西：

**一、答辩 PPT 文件**（`答辩PPT-<项目简称>-<YYYYMMDD>.pptx`）
按参考模板排版，可直接放映、可继续编辑，每页旁白在 PowerPoint 备注区。

**二、答辩旁白稿**（`旁白稿-<项目简称>-<YYYYMMDD>.md`，同时贴进对话）
按页对应：

```markdown
### 第2页 旁白（240字）

<旁白正文>

（……逐页到底，末尾：）
**旁白总字数：1890 字（约 9.5 分钟）**
```

**三、PPT 内容大纲 + 生成说明**（贴在对话里）

- 内容大纲：按页列出页面标题、核心要点、所用图表类型与数据来源、底部总结句、所用版式。
- 生成说明：内容取自申请书的哪些章节、哪些页**用了申请书原图**（注明来自哪一张）、
  哪些页是按原图重画的、哪些页是自己画的、哪些页缺信息、做了哪些取舍。

Markdown 分级标题排版，PPT 内容与旁白分开呈现、对应关系明确。

## 常见误区

- **没读透就动手。** 不理解项目的逻辑就写不出好要点，也画不出好图。先读完整条主线再排页。
- **把申请书段落直接搬上幻灯片。** 一页要塞下三四百字，字小到讲不了。要提炼成 3–5 条要点，
  而且是换了说法之后的短句，不是把长句砍掉半截。
- **把旁白写成了朗读稿。** 旁白是补充说明，不是把要点念一遍；也注意别把总结句原样复述。
- **研究内容与页数对不上。** 先数清研究内容有几项，再定页数，不要先按 14 页排好再硬塞。
- **把研究现状写成"某人做了某事，仍有不足"。** 那不叫现状分析。要写清这条路线**怎么做**
  （原理），再由原理推出它**缺什么**。
- **总结句写成散文。** 研究内容页是"针对…问题，已有方法…不足，研究…技术"，
  技术路线页是"提出/设计…方法，相比于原有…，优势在于…"。总结框只有一行，写长就缩字。
- **第 2 页写得太薄。** 这一页评审看得最细，材料不足时宁可回头找用户补，也不要凑数。
- **研发明、编项目。** 申请书里没有的论文和项目，一个都不许出现。
- **有原图却不用。** 申请书该节有能对上的图，先复制进来用；别放着现成的图不用去自己画。
- **把图表槽留成「图/表」。** 那是模板占位，不是成品。申请书没图也要按 figure-spec 画一张。
- **把重画的图做成文字表格。** 格子里填句子不是图。需求、现状画逻辑链，技术路线画带箭头的分层流程。
- **技术路线只有一张简图。** 右侧必须有要点；图本身要有步骤和子步骤，三个空框不算技术路线。
- **图只求填满，不求好看。** 框不对齐、留白忽大忽小、节点挤成一团，评审一眼就看出是凑的。
  简洁是"只讲一件事"，不是"随便摆几个框"。
- **原图看不清还硬嵌。** 申请书图在 17 cm 槽里字读不出，或只是表格截图，就重画。
- **图串页。** 研究内容页出现申请书其他章节的架构图，属于用错出处，必须换掉。
- **用假数据凑柱状图。** 没有量化数据就改画结构图。
- **字号一刀切。** 模板 16 磅是默认值，不是法令；框里放得下就保持，放不下就降，不要为了固定磅值去硬截句子。
- **旁白超字数。** 写到 2400 字讲 12 分钟会被打断；写完必须统计。
