# 图表生成规范

模板正文页的图表槽（`矩形 2`）只是一块 accent1 色块加「图/表」三字，
**不是成品图**。交付的 PPT 必须把这块换成真正的图。风格、配色、几何
全部跟 `assets/template.pptx` 走。

**图表只有一个模块：`scripts/shapes.py`。**

- 自己画的图 → `render_shapes()` 生成 **PPT 原生形状**（圆角矩形、文本框、箭头、
  饼图扇区），在 PowerPoint 里能点选、改字、挪框、换色。
- 申请书原图（`type: image`）→ `render_image()` 按槽位等比缩放居中，写成 PNG。
  原图本来就是一张现成的图，不重画也不改它的内部结构。
- `to_preview_png()` 把画布按同一套几何画成 PNG，供生成后自查版式
  （有没有压字、出框）；PowerPoint 里的实际效果以形状为准。

位图渲染（早先的 `draw_figure.py`）已经删掉：它和 `shapes.py` 各实现了一遍同样的
九种图，两边的数量上限、字号、间距迟早会分叉——事实上已经分叉过。
一套图只留一份实现。

一句话概括这份规范：**图要美观、简洁，而且一眼看得出结构。**

## 一、硬规则

1. **美观、简洁，但不简陋。** 一张图只讲一件事，层次清楚、框对齐、留白均匀，
   同一页里的节点大小一致，颜色只用模板主题色。不要为了填满槽位而堆节点，
   也不要把三五个框随便一摆就交卷——图里必须能看出关系：谁包含谁（分层框架）、
   谁先谁后（流程）、谁导致谁（逻辑链）。看不出关系的图，等于把文字换了个排法。
2. **风格跟模板，不另起炉灶。** 配色只用主题色：accent1 `#5B9BD5`、accent2
   `#ED7D31`、accent5 `#4472C4`、accent6 `#70AD47`、accent4 `#FFC000`、
   accent3 `#A5A5A5`、dk2 `#44546A`。白底、细描边、无阴影堆砌、无装饰插画。
3. **用原图还是自己画：三条路，按顺序试。**
   1）**申请书该节有能对上的图 → 复制过来用。** `extract_doc.py` 抽到 `_media/`，
      按 `{"type": "image", "path": ...}` 嵌入，生成说明里注明来自申请书哪一张。
      复制过来后**酌情处理**：图注、边框、水印、大片留白可以裁掉再嵌，
      整页宽的图裁出核心区域。
   2）**原图方向对但画得糙、或投影下看不清 → 按它的结构重画。** 保留原图的骨架
      （分层就还是分层，流程就还是流程），用本脚本的 `flow` / `framework` /
      `logic` / `compare`，或先用绘图工具出 PNG/SVG 再按 `image` 嵌入。
      原图只是表格截图时，也走这条。
   3）**申请书没有图 → 自己画，而且要仔细画。** 先读透该节，把结构、步骤、层次
      都理出来再动手：节点该有几个就画几个，每步该有子动作就挂 `children`，
      不要交一张只有三个空框的简图。画完自己看一眼——能不能看出这个项目在做什么、
      分几步、谁驱动谁；看不出来就回去补。
      用外部工具画的图同样受字号下限约束，别把一整页流程图缩成看不清的小字嵌进来。
4. **不编数据。** 柱状图、饼图、对比表里的数字必须来自申请书。没有量化数据
   时改画结构图（流程 / 框架 / 卡片 / 对比栏），不要用假数字凑一张柱状图。
5. **必须是图，不是文字表格。** 槽位 17.06 × 9.03 cm。自己重画的图默认是流程、
   逻辑链、分层框架或左右对比，节点之间要有箭头或层级关系。**禁止**用
   `table` / `cards` 把申请书段落改写成格子里的句子交差——那看起来是图，
   读起来是文字罗列，而且格子一多字就看不清。`table` 只留给「主要技术指标」
   这种本来就是指标对照表的页；`cards` 只留给第 2 页的四个栏目和第 11 页的成果分类。
   密度上限（`shapes.py` 已按此写死，超出的项会被截掉）：流程 ≤5 步（每步 ≤3 个子步骤）、
   逻辑链 ≤4 环、框架 ≤4 层（每层 ≤4 项）、卡片 ≤4 张（每卡 ≤3 行）、
   对比每侧 ≤4 条、饼图 ≤5 块、表格 ≤5 行、柱状 ≤6 条、甘特 ≤6 条。塞不下就删次要项，
   **不许再把字号降到看不清**。
6. **任何"标签带 + 内容框"的结构，标签必须有独立行高。** 层名、时间轴刻度、表头
   这类文字，要先按字号算出它自己占多高（`shapes.py` 里用 `_title` / `axis_h` /
   `name_h` 这类量），内容框从它下面再开始，不能共用同一段 y 区间。
   内容框一律**不填色**（透明，只留描边）——这样即使挨得近，也不会出现"白框盖住
   层名"这种事故。分层框架的层名被遮、甘特图的「1–6 月」被柱子压住，都是这个原因。
7. **图内文字 16–18 磅**（下限 14 磅）。图里的文字是真文本，`sz` 直接写磅值，
   跟分辨率无关——所以不存在"图糊了就把字调小"这种事。装不下就减节点、
   把长句拆到右侧要点里。一个节点里的标签控制在 8 个汉字以内。
8. **图文同页对应，且不许重叠。** 图里出现的标签、数字、阶段名，必须能在右侧
   要点或申请书原文里找到出处。图只占图表槽，正文只占文字槽；不要把申请书原图
   （往往带自己的图注、坐标轴小字）直接铺满槽位后，再在旁边堆一段会压到图上的文字。
9. **画图之前先把那一节读完。** 这是本技能最容易出错的地方：需求分析、研究现状
   这类页，把要点抄进格子不算图。要读完该节，找出**因果关系**——痛点是什么、
   为什么会成为缺口、本课题怎么回应——再用 `logic` 画成带箭头的逻辑链。
   同理，技术路线要读「研究思路方法与技术路线」那几段，抽出实现步骤和每步的动作，
   用 `flow` 画成分层流程；研究内容要读出「具体研究内容」里的部件划分，用
   `framework` 画成分层结构。
10. **只取本页对应章节的事实。** 研究内容 N / 技术路线 N 不得搬其他章节的架构
    （典型错误：研究内容页出现申请书里另一处的「平台架构框图」）。

## 二、按页选图（默认）

| 页 | 默认 type | 备选 | 画什么 |
|---|---|---|---|
| 第 2 页 积累 | `cards` | `image`（论文封面/项目 logo 拼贴，且投影下字能看清） | 四个栏目各一卡：**发表论文 / 项目经验 / 合作厂商 / 编译优化**，每卡 ≤3 行短句，写清「多少篇 / 什么级别 / 哪些项目 / 哪些厂商 / 覆盖多少优化点」。栏目句式见 `references/content-spec.md` |
| 第 3 页 需求 | `logic` | `compare` | 读完需求分析那几段，画因果链：痛点 → 现状/缺口 → 本课题回应，底部一条结论带。不要左右两栏抄要点 |
| 第 4 页 现状 | `logic` | `compare` | 读完研究现状，画：各条路线在做什么 → 它们共同的不足 → 本课题的方向。同样要箭头，不要文献罗列 |
| 第 5 页 概述 | `framework` | `flow` | 总体方案分层（问题层 / 方法层 / 运行层），把两部分研究内容和它们的接口画进同一张图，别只放一个空壳 |
| 研究内容 N | `framework` | `flow` | 该内容的目标 / 关键技术 / 产出，分层，不画成条目表 |
| 研究技术路线 N | `flow`（带 `children`） | `framework` | **必须是带步骤关系的流程图**，3–5 步，每步可挂 2–3 个子步骤。申请书没有路线图时，按该节文字把实现路径画成分层流程，不要交一张只有三个空框的简图，也不要只放图、右侧不写要点 |
| 主要技术指标 | `table` | `bar` | 指标名 × 预期值（有对比列就加一列）。这是唯一默认用表的页 |
| 成果及考核 | `cards` | `flow` | 论文 / 专利 / 软著 / 系统 各一张卡，每卡一行数量 |
| 周期与进度 | `gantt` | `flow` | 阶段 × 时间轴；阶段名写短 |
| 经费预算 | `pie` | `bar` | 科目占比；科目 ≥6 个时改用水平条 |

封面、结束语不配图。申请书里有更贴切的原图时，把该页 `type` 改成 `image`。

## 三、JSON 契约（写入每页的 `figure`）

`figure` 必须是对象，不要再写成一句配图说明。`scripts/build_ppt.py` 读这个
对象，调用 `shapes.py` 生成一组 PPT 原生形状，插进图表槽（`type: image` 才走位图）。

公共字段：`type`（必填）、`title`（选填，画在图内顶栏）。

### `image` — 复用申请书原图

申请书该节有能对上的图时，**这是首选**：把它复制进 PPT，而不是另画一张。
`extract_doc.py` 会把内嵌图片抽到 `申请书_media/`，直接指过去即可。
`caption` 写原图的图题（有就写，没有可省）。

```json
{ "type": "image", "path": "申请书_media/image3.png", "caption": "图1 总体技术框架" }
```

嵌入前**酌情处理**：图注、边框、水印、大片留白先裁掉；只截核心区域也可以
（用 `PIL` 或任意图像工具裁好再指过去）。原图字在 17 cm 槽位里太小、
或它本身就是一张表格截图时，改成按它的结构重画，不要硬嵌。

### `table`

```json
{
  "type": "table",
  "title": "主要技术指标",
  "columns": ["指标", "预期", "对照"],
  "rows": [["编译时长降幅", "≥30%", "现有工具链"], ["通过率", "≥95%", "基准测试集"]]
}
```

### `bar` — 水平条（适合科目名较长）

```json
{
  "type": "bar",
  "title": "经费构成",
  "unit": "万元",
  "items": [
    { "label": "设备费", "value": 40 },
    { "label": "材料费", "value": 25 }
  ]
}
```

分组对比用 `values` + `series`：

```json
{
  "type": "bar",
  "title": "指标对照",
  "series": ["现有", "本课题"],
  "items": [{ "label": "吞吐", "values": [1.0, 1.4] }]
}
```

### `pie`

```json
{
  "type": "pie",
  "title": "经费预算",
  "unit": "万元",
  "items": [
    { "label": "设备费", "value": 40 },
    { "label": "劳务费", "value": 30 },
    { "label": "其他", "value": 10 }
  ]
}
```

### `gantt`

`start` / `end` 是时间轴的下标（从 0 起，半开区间：`end` 不包含）。

```json
{
  "type": "gantt",
  "title": "进度安排",
  "axis": ["2026Q1", "Q2", "Q3", "Q4", "2027Q1", "Q2"],
  "items": [
    { "name": "需求分析与方案", "start": 0, "end": 2 },
    { "name": "核心算法实现", "start": 1, "end": 4 }
  ]
}
```

### `flow`

技术路线页用带 `children` 的分层流程。`children` 里每一项是该步的子动作，
脚本会画成阶段框 + 框内子步骤 + 阶段间箭头。没有 `children` 时退回一排步骤框，
只适合 3–4 个很短的步骤，不适合技术路线。

```json
{
  "type": "flow",
  "title": "技术路线一：编译到执行",
  "steps": [
    { "label": "前端", "children": ["源语言解析", "IR 构建"] },
    { "label": "优化", "children": ["数据流分析", "目标无关优化"] },
    { "label": "后端", "children": ["指令选择", "寄存器分配"] },
    { "label": "执行验证", "children": ["基准测试", "结果对照"] }
  ]
}
```

### `framework`

```json
{
  "type": "framework",
  "title": "总体方案",
  "layers": [
    { "name": "问题层", "items": ["语义鸿沟", "优化空间"] },
    { "name": "方法层", "items": ["表示", "分析", "生成"] },
    { "name": "验证层", "items": ["基准", "案例"] }
  ]
}
```

### `logic` — 逻辑链（需求分析、研究现状）

节点之间是因果关系，箭头本身就说明「为什么」。写之前先把该节读完，
每个节点一句短话，不要整段抄。

```json
{
  "type": "logic",
  "title": "需求分析：存储墙到编译缺口",
  "nodes": [
    { "label": "痛点", "desc": "计算与存储分离，访存主导推理时延与能耗" },
    { "label": "现状", "desc": "编译与编排均面向 GPU 统一地址空间" },
    { "label": "缺口", "desc": "多单元独立编址、跨单元须经主机，无人适配" }
  ],
  "foot": "本课题：面向存算一体架构的 AI 编译软件栈"
}
```

`nodes` 2–4 个，`foot` 是底部那条结论带（可省）。节点标签 ≤6 字，`desc` 一到两句。

### `compare`

```json
{
  "type": "compare",
  "title": "研究现状",
  "left": { "title": "现有方法", "points": ["依赖手工规则", "跨架构泛化弱"] },
  "right": { "title": "本课题", "points": ["可学习表示", "多后端统一 IR"] }
}
```

### `cards`

```json
{
  "type": "cards",
  "title": "编译领域积累",
  "items": [
    { "title": "论文", "lines": ["CCF-A 会议 3 篇", "SCI 一区 2 篇"] },
    { "title": "项目", "lines": ["国家重点研发 课题骨干", "自然科学基金面上"] }
  ]
}
```

## 四、画不出时的退路

1. 自己画的图走 `shapes.render_shapes()`，**不需要 Pillow**。只有两种情况下才依赖它：
   `render_image()` 嵌申请书原图，以及 `to_preview_png()` 出自查预览图。
   缺 Pillow 时原图那条路会失败并退回文字说明，先 `pip install pillow`。
2. `type` 不认识或数据字段缺失：该页退回文字说明，并在生成说明里写原因。
3. 申请书原图格式古怪（wmf/emf）：抽得出就尝试；打不开就按本页默认 type 重画。

## 五、自检

- [ ] 除封面、结束语外，每一页图表槽都是图，没有「图/表」三字
- [ ] 申请书该节有可用原图的页，已把原图复制进来并酌情裁切，来源写进生成说明
- [ ] 自己画的图是 PPT 原生形状（脚本报告里显示"形状图 N 个（可编辑）"），
      在 PowerPoint 里点得开、改得动
- [ ] 自己重画的图是流程 / 逻辑链 / 分层框架 / 左右对比，不是把句子填进格子
- [ ] 自己画的图够丰富：结构、步骤、层次都在，不是一张三个空框的简图
- [ ] 图美观简洁——框对齐、留白均匀、颜色只用主题色，一眼看得出关系
- [ ] 层名 / 轴标签 / 表头都有独立行高，内容框不填色，没有被白框或柱子压住
- [ ] 用 `shapes.to_preview_png()` 出过预览图，肉眼看没有压字、出框
- [ ] 需求分析、研究现状两页画的是带箭头的逻辑链，读得出「痛点→缺口→回应」
- [ ] 技术路线页的图带步骤、子步骤和箭头（有 `children`），不是三个空框；右侧同时有要点
- [ ] 配色只有模板主题色，没有额外的红绿撞色或渐变
- [ ] 饼图/柱状图/表格里的数字能在申请书里找到
- [ ] 图内文字 16–18 磅；把 PNG 打开，肉眼能读出每个节点
- [ ] 图没有压到正文，正文框与图表槽上下沿对齐
- [ ] 用了申请书原图的页，在生成说明里注明来源；弃用原图（字太小、是表格截图、
      或主题对不上，例如把别的架构图塞进研究内容页）也要注明原因，以及是重画还是自绘
