# 审查规范（两道门禁）

做 PPT 最容易出的问题不是"不会做"，而是"做完没查"：素材没收就开始画、
图画完没看就交付、研究内容页只讲了现状没讲方法。所以流程里设两道门禁，
**不通过不许往下走**。

| 门禁 | 时机 | 脚本 | 不通过时 |
|---|---|---|---|
| A 过程审查 | 画图之前 | `scripts/audit_process.py` | 回到素材收集或图表规划 |
| B 质量审查 | 生成 pptx 之后 | `scripts/audit_quality.py` | 按问题类型回退，见第三节 |

两个脚本都是 `退出码 0 = 通过`、`2 = 有阻塞项`。阻塞项必须改掉，
提示项要逐条看过再决定接受还是改。**脚本通过不等于做完**——
脚本查得出几何和措辞，查不出"这一页看着好不好"，所以还要逐页看预览图。

---

## 一、过程审查（门禁 A）

```bash
python3 scripts/audit_process.py --assets work/assets/index.json \
        --plan work/figure-plan.json
```

| # | 查什么 | 判定 | 不通过回到 |
|---|---|---|---|
| 1 | 收过素材 | 有 `index.json`，且每份素材「包内图片文件数 = 抽出图片数」 | 重跑 `collect_assets.py`，docx 的 `a:blip` 与 `v:imagedata` 两种写法都要抽 |
| 2 | 素材分过类 | 没有 `kind` 还是「未分类」的图 | 逐张看图，标成厂商标识 / 论文或证明 / 性能曲线 / 架构图 / 指标表 / 经费表 / 进度表 / 流程图 / 其他可用 / 用不上 |
| 3 | 每个图槽都做过选择 | 每槽 `source` ∈ asset / draw / external | 补填规划，不许留空 |
| 4 | 用素材的槽，精度够 | 铺到该槽尺寸后有效 DPI ≥ 110；不够要在 `decision` 里写明重画/放大/换图 | 像素够就放大铺满；不够就按原图结构重画 |
| 5 | 每槽都写了尺寸与用途 | `w`/`h` 来自模板实测，`purpose` 一句话说清这张图讲什么 | 先跑 `plan_figures.py --slots` 量尺寸，再想清楚画什么 |
| 6 | 厂商标识有来源 | 素材里有「厂商标识」类图，或 `decision` 里记了搜过的关键词 | 先从素材找，再逐家搜官方标识；搜不到的写明是哪家、试过什么词 |

### 第 3 步的两件事：先定张数尺寸，再定用谁的图

**先定张数和尺寸。** 模板里这一页有几个矩形就规划几张图，每张写明宽高。
`plan_figures.py --slots` 打印实测尺寸。半槽（高 < 6 cm）最多放 3 层或 3 行，
不要在半槽里画 4 层框架。只在这一页本来只需要一张图时，才把它铺满全部矩形的外接区域。

**再定用素材还是自己画。** 每个矩形都要在"原图"和"自己画"之间**显式选一次**，
把选择理由写进 `decision`，不许默认一律自己画：

| 情况 | 怎么办 |
|---|---|
| 素材里有能对上的图，像素够 | 直接用，放大到铺满这个矩形，只裁四周空白和无关内容 |
| 素材里有，但铺到这个尺寸不足 110 DPI | 按它的结构重画（分层还是分层、流程还是流程），或换一张 |
| 素材只是表格截图 | 按它的行列重画成 `table`，不嵌截图 |
| 素材里没有 | 自己画；复杂到画不动时用外部工具出 PNG/SVG 再嵌（见 figure-spec 第一节第 3 条） |
| 确实做不出来 | 才允许 `source: pending`，并在生成说明里写明缺的是素材、标识还是尺寸 |

**素材看着小 ≠ 像素不够。** 素材在原 PPT 里被放小是常事，先看文件本身的像素，
不看它原来的显示尺寸。`清单.md` 里直接给了「铺到 17 cm 的 DPI」这一列。

## 二、质量审查（门禁 B）

```bash
python3 scripts/audit_quality.py --pptx 答辩PPT.pptx --content content.json
```

八条，与用户验收口径一一对应：

| # | 查什么 | 判定 | 不通过回到 |
|---|---|---|---|
| 1 | 页数 | ≥ 14 页 | 图表规划：按申请书的研究内容项数补页（每项 2–3 页） |
| 2 | 页内不重叠 | 正文框与图元素无 > 0.12 cm 的双向重合；所有形状在页面内 | 图表规划：调槽位或收窄正文 |
| 3 | 图内不遮挡 | 图内两框无双向重合、无出框、文字不被截 | 绘图：减节点、加间距或换图型 |
| 4 | 没有占位 | 全文无「待补充」「图/表」「xxx」 | 素材收集或绘图：每页都要有真图 |
| 5 | 尺寸布局字号 | 图内 14–18 磅、正文 ≥ 12 磅、图没缩在一角 | 绘图：按槽位尺寸重排 |
| 6 | 总结句能概括本页 | 有总结句、不含空话、与本页要点说的是同一件事 | 内容：重写这一句 |
| 7 | 研究内容第 1 页 | 每个技术项都写了「传统不足」和「我们设计/提出的方法」 | 内容：按第三节的三段式重写该项 |
| 8 | 第 4 页研究现状 | 写了已有方法的缺陷，且除总述外每个模块都有不足 | 内容：逐模块补上不足 |

### 第 6 条：总结句的标准

总结句要落在"这一页做完得到什么"上，而且必须是**这一页**的结论。两类不合格：

- **空话**：「意义重大」「前景广阔」「效果良好」——换成哪一页都成立的，就不是总结。
- **口号**：和本页要点没有共同说法的另起一句。脚本按二字片段比对，命中太少会提示。

### 第 7 条：研究内容第 1 页怎么体现创新

**不要写「创新」二字。** 写上「创新点」「具有创新性」是空话，评审看的是你究竟做了什么。
创新由「设计/提出了什么方法」本身体现。每个技术项按三段写：

1. **传统做法哪里不行**——用否定词把缺口说实（未抽象、无法表达、难以适配、不成立）。
2. **我们设计/提出了什么方法**——用「设计了/提出了/建立了/实现了〈方法名〉」，方法要有名字。
3. **落点**——这个方法覆盖什么、带来什么（可选，但有了更完整）。

```
图编译器：整模型单设备假设不成立
  · 传统图级IR未抽象存储分块与设备归属      ← 不足
  · 设计图级中间表示与子图拆分映射方法      ← 方法
  · 按计算/访存均衡切分并自动插入搬运同步    ← 落点
```

反例：「图编译器：负责图级编译 / 把计算图映射到硬件 / 包含拆分与映射」——
三条都在说现状，一条方法都没有，评审读不出这项内容到底做了什么。

脚本按词表判断，词表宽松（漏判好过误拦）：只要这一项里一个否定词都没有，
或者一个「设计/提出/建立」都没有，就是真没写。

### 第 8 条：研究现状怎么写缺陷

按「先总后分」：总述写这个软件栈是什么、包含哪几个模块、**总体缺什么**；
其后每个模块写职能 + **它的不足**。只写职能不写不足的模块，脚本会逐个点名。

## 三、回退映射

质量审查不通过时，按问题类型回到对应阶段，**不要就地微调糊过去**：

| 问题 | 回到哪个阶段 | 做什么 |
|---|---|---|
| 图文重叠、图超页面 | 图表规划 | 重排槽位或改图数 |
| 图内遮挡、节点挤 | 绘图 | 减节点、加间距、换图型 |
| 缺图、留占位 | 素材收集 / 图表规划 | 补素材，或把该槽改为自己画 |
| 正文溢出 | 内容 | 按第四节的阶梯处理 |
| 总结句空泛、研究内容页缺方法、现状页缺缺陷 | 内容 | 重写该页要点 |
| 页数不足 | 图表规划 | 按研究内容项数补页 |

## 四、文字折叠的处理阶梯

正文溢出不许靠"硬压字号"解决，按顺序试，前一步能解决就不用后一步：

1. **缩减字数**（首选）。先想清楚这条到底在说什么，再换更短的说法，
   不要把原句截断。一级标题压到 28 字内、二级行压到 24 字内。
2. **拓宽文本框**。正文框与图槽之间还有余量时，加宽正文框；
   加宽后必须复查它没有压到图槽（质量审查第 2 条会查）。改了几何要记进生成说明。
3. **降字号**。一级 18 → 16 磅，二级 16 → 14 磅，下限 12 磅。
4. **砍二级行**。12 磅仍溢出，说明这一页装不下，删掉最弱的那条二级行。

图内文字同理：先缩短文字，再换更矮的图型（4 层框架换成 3 层、或改用对比栏），
最后才降字号，下限 14 磅。

## 五、脚本查不到、必须人看的部分

两道门禁都通过之后，还要做这三件事，缺一不可：

- [ ] **逐页看预览图**（`preview_slides.py`）：图读不读得清、图文是否挤在一起、
      一页是否一边满一边空。没看过的页不算完成。
- [ ] **逐张图单独看**（`shapes.to_preview_png`）：按该矩形的真实宽高渲 PNG，
      看图里能不能看出这个项目在做什么、分几步、谁驱动谁。看不出来就回去补。
- [ ] **逐条核对出处**：页面上每个数字、每条结论都能在申请书原文或用户给的
      团队资料里指出来源。指不出来的删掉，不要留着。
