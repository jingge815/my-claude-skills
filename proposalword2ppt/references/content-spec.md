# 逐页内容规范

这份文件回答一个问题：**每一页到底该写什么、怎么写**。
写 `content.json` 之前通读一遍；`SKILL.md` 讲的是流程和原则，具体到页面的措辞在这里。

页码按标准 14 页方案（研究内容 2 项，每项 2 页）。研究内容多于两项、或某一项确有独立的过程图时，
该研究内容连续占 3 页，其余页不变。同一研究内容的每一页标题相同，写成「研究内容N：主题」。

要点一律写成对象，旧的「标签：说明」字符串仍然接受：

```json
{ "label": "中间表示", "text": "传统表示未考虑存算一体特性",
  "subs": ["设计两级分层专用中间表示，实现图算协同", "原生植入近存语义"] }
```

`label` 是一级标题，`text` 是主句，`subs` 是二级行，最多 3 条。

一级标题和二级行**不能同一字号、也不能同一左沿**。一级标题用正文磅值（16 磅起），二级行小 2 磅，并在一级标题的左缩进上再缩进约 0.85 cm。二级行以「·」开头，单独成段。

---

## 第 1 页 封面（`cover`）

| 元素 | 规格 |
|---|---|
| 标题 | 项目申请书完整全称。**微软雅黑、默认 44 磅、居中**；标题过长脚本降到 40 / 36 / 32 磅 |
| 副标题 | **必填**，24 磅。默认「重点实验室自主科研项目评审答辩」；申请书封面写的项目类别不同，就换成那个类别加「评审答辩」。不留空 |
| 右下角四行 | `报告人：〈姓名〉` / `单位：〈单位〉` / `职位：〈职务〉` / `〈YYYY年MM月DD日〉`，四行都是 20 磅。单位默认中国科学院软件研究所，`org` 可覆盖 |

职位按本项目的材料写（高级工程师、副研究员等）。材料里没有就向用户要，不要猜一个。
日期取答辩日期，没给就向用户要，不要自己填一个。
副标题没有就不生成这一页的封面，先向用户确认项目类别。

## 第 2 页 编译技术积累（`accumulation`）

这页是核心考核项，**固定写四条**。每条可以挂二级行：

| 栏目 | 主句 | 二级行 |
|---|---|---|
| 发表论文 | 发表〈篇数〉篇〈方向〉相关国内外高水平论文 | CCF-A 〈n〉篇、CCF-B 〈n〉篇（或材料里的同等分级） |
| 项目经验 | 一句评价：是重点研发方向，获〈哪些专项〉长期支持 | 牵头或参加的代表项目、编译器数量 |
| 合作厂商 | 一句评价：与〈哪些类型〉厂商保持长期深度合作 | 厂商名录 |
| 编译优化 | 含金量最高的量化结果，例如某编译器在某基准上的成绩 | 优化点规模、覆盖的技术方向 |

规矩：

- **内容一方面要仔细看项目申请书，同时仔细阅读用户给你指定的团队资源积累资料。** 这两方面资料都要统计，没有就问用户，不要自己编。
- **论文按团队口径统计，不只算负责人。** 申请书研究基础里常把几位老师的工作分列，要合进「发表论文」这一条，按级别归并。别漏掉不是负责人署名的那几篇。
- **论文主句必须含「国内外高水平论文」。** 级别和篇数放在二级行，不另起一条一级标题。
- **项目经验和合作厂商不能只报名单。** 评价句用材料里真有的事实来撑（长期支持、重点方向、深度合作），没有依据就不要加这几个词。
- **数字只能来自申请书或用户补充。** 编译优化优先写材料里含金量最高的那一个量化结果；没有就把已知事实写上并标注「（性能数据待补）」，同时在生成说明里请用户提供——**不许编一个数字**。
- 「合作厂商」申请书里通常没有，来自用户补充；用了在生成说明里注明来源。
- 不要把文献条目逐条抄上去，也不要写「研究条件/实验室环境」——它们不占那四条的位置。
- 底部总结句落在一个判断上，例如「编译方向积累深厚、论文含金量高、项目经验丰富，具备承担本项目的技术实力」。
- 图用 1–3 组：一张性能或技术演进图（材料里有原图就用 `image`，没有就 `framework`），加上一组 `logos`（合作方标识、论文或证明材料的截图）。`logos` 里路径打不开的项会被跳过并在校验里报告。

## 第 3 页 需求分析（`text-left`）

一级标题本身是一条逻辑链，后一条接前一条，不要并列堆背景。标题用内容本身，不要写成「重要性」「瓶颈」「缺口」这种点评词——重要性要靠这一句讲出来，而不是直接说「很重要」：

1. 这件事关系到什么（对象是什么、卡在谁身上），不出现「重要」二字。
2. 哪个瓶颈制约它的性能或成本，有量化依据就写进二级行。
3. 哪条途径是解决这个瓶颈的方法。
4. 因此需要什么样的软件栈，以及它和现有栈差在哪。

主句可以到约 44 字，每条下面最多 3 条二级行。图用 `logic` 画同一条因果链；材料里有架构对照或关键数据图时，作为第 2 组图。

## 第 4 页 研究现状（`text-left`）

**这页最容易写成文献清单，而且最容易只写职能、不写缺陷。** 按「先总后分」写：

- 第一个一级标题是总述：这个软件栈（或系统）是什么、包含哪几个技术模块、**总体上缺什么**。
- 其后每个一级标题是一个模块。二级行写两件事：它的职能（基于什么、把什么映射成什么），
  以及**它的不足**——这一条是本页的重点，不是可选项。
- 申请书里一个主题拆成多个模块时，总述里先写模块之间的关系（谁给谁输入、谁约束谁），再分模块写。

**每个模块都要点出已有方法缺什么**，否则这一页只是在介绍别人的工作，
读不出本项目为什么还要做。缺陷要具体到机制层面，不写「不够完善」这种泛词：

```json
{ "label": "核心编译器", "text": "三层面存在系统性不足",
  "subs": ["IR未抽象近存与分块", "代价模型未耦合访存", "优化停在功能跑通"] }
{ "label": "编排器", "text": "依赖GPU统一地址空间",
  "subs": ["vLLM、SGLang等主流框架", "缺跨步驻留与多单元协同"] }
```

`audit_quality.py` 第 8 条会检查：全页至少有缺陷表述，且除总述外每个模块都写了不足；
只写职能的模块会被逐个点名。

图用 `framework` 把模块关系画出来；材料里有可核对的差异维度（地址空间、通信、内存、容量这类）时，加一张 `table`。不要用表替代总述文字。

## 第 5 页 研究概述（`figure-left`）

这是概括，不是后文的预演。右侧：

- 第一个一级标题写研究目标，用一句话，不说「两项内容」。
- 其后每个一级标题直接用该研究内容的主题（如「核心编译优化方法」），不要写成「研究内容一」。二级行只点到子研究点（提出什么、建立什么、设计什么），不写方法怎么实现。

左图是一张总框架，块名与右侧的研究内容、子研究点用词一致，不画步骤。**禁止把第 6 页以后的方法细节提前写完。**

底部总结句同时点出研究问题和解决思路，一行放下。

## 研究内容页（`figure-left`，每项连续 2–3 页）

标题统一写成「研究内容N：〈主题〉」，同一项的每一页标题相同。

**第 1 页讲技术本身。** 右侧一级标题是这项内容的子研究问题（例如中间表示、评估模型、编译优化）。每个一级标题下面的二级行按这个顺序，三段都要有：

1. **传统做法哪里不行**——用否定词把缺口说实（未抽象、无法表达、难以适配、不成立、开销大）。
2. **我们设计或提出了什么方法**——用「设计了 / 提出了 / 建立了 / 实现了〈方法名〉」，方法要有名字。
3. **落点**——这个方法覆盖什么、带来什么。

**创新靠方法本身体现，不要写「创新」二字。** 幻灯片上写「创新点」「具有创新性」是空话，
评审看的是你究竟设计了什么、和传统做法差在哪。把第 1、2 段写实，创新自然就在那里了。

```json
{ "label": "图编译器", "text": "整模型单设备假设不成立",
  "subs": ["传统图级IR未抽象存储分块与设备归属",
           "设计图级中间表示与子图拆分映射方法",
           "按计算/访存均衡切分并自动插入搬运同步"] }
```

反例：「图编译器：负责图级编译 / 把计算图映射到硬件 / 包含拆分与映射」——
三条都在讲现状，一条方法都没有，读不出这项内容到底做了什么。
`audit_quality.py` 第 7 条会逐项检查这两段，缺哪段点哪段。

左图用 `framework`，分区名与右侧一级标题同名。图的标题用这项内容在做什么（如「图级与算子级协同」），不要写成「三个子问题」「两个模块」这种清点数量的话。

**第 2–3 页讲过程。** 左图用 `flow`，3–5 步，每步挂 `children`。右侧一级标题与步骤对应，二级行写这一步做什么、产出什么。只有确有另一张独立的过程图时才用第 3 页。

**底部总结句是一句话，说这一页做完得到什么，不套「针对……，设计……」。**

- 研究概述：全流程要打通到哪一步、做到之后释放什么。
- 研究内容第 1 页：面向什么特性形成什么体系，点出两部分怎么配合。
- 过程页：从哪一端到哪一端，中间按什么顺序推进。
- 指标、成果、周期、经费：各用一句判断收住（验证什么能力、以什么提交考核、分几段推进、经费以什么为主）。

例：面向存算一体硬件特性原生设计编译体系，形成图级决策向下驱动、算子级代价反向支撑的全链路编译流程。

**总结句必须概括本页核心，而且是这一页的核心。** 两类不合格：

- **空话**：「意义重大」「前景广阔」「效果良好」「十分必要」——
  换到哪一页都成立的句子，不是总结。
- **口号**：和本页要点说的不是同一件事，等于在页脚另起一句标语。
  `audit_quality.py` 第 6 条按二字片段比对总结句与本页要点，命中太少会提示。

三条通用规矩：

- **总结框只有一行高**（1.13 cm，下面紧挨页码框，加高会撞上）。所以总结句要写成
  **一句话、一行放下**，16 磅时约 52 字；脚本报告里总结句掉到 14 磅以下就是写长了，回去改短。
- 总结句里的做法和结果必须是**申请书里真有的**，不能自己拔高。申请书写得笼统时，
  用它的原词概括，不要引入申请书没有的说法。
- 模板第 3、4 页没有总结槽，这两页不写总结句；第 3 页靠逻辑链底部的结论带收束，
  第 4 页靠最后一个一级标题的总体判断收束。

## 第 10 页 主要技术指标（`figure-left`）

申请书里通常没有百分比，**不要编数值**。按「能力 × 验收口径」把指标分类写清楚，
图用 `table`（唯一默认用表的页）。把该节内容读全——指标往往是好几段，
不要只挑第一条。

## 第 11 页 研究成果及考核方式（`figure-left`）

预期产出（论文 / 专利 / 软著 / 原型系统）与验收考核标准，逐条对应申请书。
图用 `cards`，每类产出一张卡。

## 第 12 页 研究周期与进度安排（`figure-left`）

总周期、分阶段任务、关键节点。图用 `gantt`，横轴用阶段名（如「1–6 月」）。
**轴标签要占独立的一行高度**，柱子从轴下面开始——否则标签会被柱子压住。

## 第 13 页 经费预算（`figure-left`）

右侧**只有一级标题，不挂二级行**。每行写成「科目：金额，用途」：

- 总经费：〈金额〉万元，研究周期〈几年〉
- 职工薪酬及劳务费：〈金额〉万元，保障研发投入
- 材料费：〈金额〉万元，用于研发与实验配套耗材
- 事务费：〈金额〉万元，用于调研、交流与技术咨询
- 管理费：〈金额〉万元，按总经费的比例计取

金额和科目只取申请书经费表。零值科目不进正文，也不进图。
图用 `pie`（非零科目 ≥6 个改用 `bar`）。

## 第 14 页 结束语（`closing`）

收尾句落在**本单位优势**上，默认用：

> 软件所在编译领域具有长期的技术积累和丰富的产品研发经验；在质量保证和国产化方面，
> 已形成覆盖技术、人力、方法和工具的综合保障能力；具备本课题所需原型系统的研制能力。

可按项目微调，但不能改成一句空泛的感谢。收尾句上限 90 字。

## 内容自检

- [ ] 第 1 页标题是微软雅黑 44 磅居中，右下角四行齐全（含职位）
- [ ] 第 2 页是「发表论文 / 项目经验 / 合作厂商 / 编译优化」四条；论文写国内外高水平并带级别篇数
- [ ] 第 2 页的每个数字都能在申请书或用户补充材料里找到，没有的生成了「待补」标注
- [ ] 第 4 页先总后分，总述写了总体缺什么，且除总述外每个模块都写了职能**和不足**
- [ ] 第 5 页只点到子研究点，没有把后面的方法细节提前写完
- [ ] 研究内容页标题是「研究内容N：主题」，同一项各页标题相同
- [ ] 研究内容第 1 页的每个技术项都写了「传统不足」和「我们设计/提出的方法」，
      方法有名字；全文没有出现「创新点」「具有创新性」这类空话
- [ ] 没有任何一页以「研究技术路线」为标题
- [ ] 所有总结句一行放得下（未压到 14 磅以下），且没有使用「针对……，设计……」的句式
- [ ] 总结句概括的是本页核心：不含「意义重大」这类空话，与本页要点说的是同一件事
- [ ] 第 1 页有副标题，右下角单位行以「单位：」开头
- [ ] 第 13 页右侧只有一级标题
- [ ] 第 10 页没有编造百分比或性能数字
- [ ] 结束语落在本单位优势上
